# 执行 Harness 异常恢复组合

日期：2026-10-24。适用：H0 v3、`solver-request-recovery-v2` 及其新冻结组合。旧 H0 v2 的 v1 传输恢复及无配置配方保持原策略。

## 1. 目标与边界

把“当前模型响应不可用”和“整个任务无法继续”分开。固定宿主继续检查异常流、限制响应体积、执行固定模型与原任务截止；执行 Harness 在这些边界内恢复当前请求，或把完整工具调用的参数错误反馈给模型。恢复不承诺消除模型/适配器产生异常输出的根因，也不改变官方评分和任务完成分规则。

此次覆盖模型请求传输、响应内容及工具参数协议异常。不自动重放已执行的工具，不处理科学测试失败、命令退出非零或评分器失败，不重启整个 Trial，不改变模型、调用设置、权限或原截止时间。新活动不恢复 token 账本，旧活动的准入兼容仍由宿主执行。

## 2. 插件与组合

源码位于 `src/execution/recovery/`。按恢复动作拆分能力，不为每一个错误码创建插件；使用原生 Cordis Service、依赖注入、插件作用域和 Agent 扩展点，不另建插件管理器或 Agent 循环。

| 插件 | 实现 | 职责 |
|---|---|---|
| `recovery-core` | `core.mjs`，服务 `phyexpRecovery` | 唯一恢复协调者，选择策略、执行等待、维护计数、响应取消、检查截止、保存证据 |
| `transient-recovery` | `transient.mjs` | 连接失败、响应不完整和明确 503 过载；重试当前模型请求 |
| `response-recovery` | `response.mjs` | 不合法参数流、持续空白、参数/响应体积超限；丢弃失败尝试并重新生成 |
| `tool-argument-recovery` | `tool_arguments.mjs` | 完整调用的 JSON/参数结构校验失败；拒绝工具执行，反馈错误并允许模型修正 |

`composition.mjs` 是默认组合入口；`policy.mjs` 是宿主和 Runner 共用的纯配置契约，不单独作为插件。协调者始终装配，`strategies` 显式列出启用策略。策略注册匹配条件、类别和动作，由协调者执行；重复注册或同一故障被多个策略匹配时拒绝继续，耗尽后不转交其他监听器追加次数。协调者以原生 prepend 监听器优先接管；宿主对引用同一恢复链的请求另外执行内容/合计准入上限，避免其他监听器叠加请求。插件共享一个目录和交付单元，不要求拆成独立 npm 包。

恢复组合目前属于固定执行基础设施，同一活动的 H0 与候选使用同一代码和配置，不计入 Meta 自主研发插件。以后研究恢复策略的贡献时，可在新冻结版本中移除/替换策略或调整配置并做对照；不能在已有活动中悄悄改变共同条件。

## 3. 两条内容恢复路径

### 3.1 未完成或失控的响应

`StreamGuard` 保留参数 128 KiB、响应 256 KiB、连续空白同时满足 4096 字节与 30 秒的默认保护，以及增量 JSON 前缀检查。流中出现不可能成立的 JSON 时立即中止当前请求；完整 block 的参数也按实际 UTF-8 字节检查，不允许适配器在 block-end 放入超过 delta 计数的大参数。

网关把允许恢复的保护失败映射为 `MODEL_OUTPUT_INVALID`，保留真实 `outputCode`，不伪装成网络错误。当前请求失败，但不永久封锁任务。原生 `agent/request-error` 重试该模型步骤；失败尝试只留在审计/attempt 记录，不拼进有效历史，不执行其中任何工具。之前完成的工具结果继续保留。

### 3.2 完整工具调用的参数错误

在大小保护以内、到达 tool-call block-end 的非法 JSON 或参数 schema 错误，可以暂存为待反馈问题；只有模型响应完整、成功结束后才进入工具阶段。未收到终止回执，或后续又发生断流，仍按失败请求恢复，不能执行已暂存的调用。

网关校验请求中声明的工具 schema。Runner 的原生单调 `tools.guard` 拒绝对应 call ID，并对工具实际 schema 再作统一检查；不依赖插件是否使用 `defineTool`。错误作为正常 tool result 留在历史，由模型生成新的合法参数。同一响应的其他合法工具可以按原生调度执行，其结果不得重放。

流中已经触发保护的非法 JSON 不等待“也许稍后完整”，继续走 3.1。delta 尚不完整而 block-end 被适配器正规化成合法参数的情况仍视为流不一致，重新生成，不执行正规化的命令。没有启用反馈策略时，完整参数错误可由响应策略重新生成；两种策略均未启用时按终止保护处理。

## 4. 统一次数、身份与生命周期

默认冻结配置：

```json
{
  "version": "solver-request-recovery-v2",
  "strategies": ["transient-recovery", "response-recovery", "tool-argument-recovery"],
  "retryDelaysSeconds": [2, 5, 20, 30, 60],
  "contentRetryDelaysSeconds": [0, 1],
  "maxChainRetries": 5
}
```

传输最多追加五次；响应重新生成和工具参数反馈共同使用两次内容恢复机会；每条恢复链合计最多追加五次模型请求。内容等待 0、1 秒为初始工程配置，并非已证实最优值。传输等待遵守更长的有效 Retry-After。取消、插件卸载和原截止会终止等待；等待将达到截止时不发下一次请求。

同一会话的主步骤和 compaction 分别维护恢复链。坏参数 → 断线 → 坏参数仍是同一链；`step/start`、`turn/end`、策略切换及辅助调用成功不能清零。只有对应链的完整、无参数问题的响应才结束恢复链。摘要失败部分整体丢弃，只有完整成功摘要提交。普通插件直接 `ctx.llm.stream` 调用不接管主循环的恢复链，仍由调用方处理；原生 compaction 单独接入恢复。

恢复状态由 `phyexpRecoveryV2` 会话投影重建，保存计数、原失败、最近请求、待反馈 call ID、停止原因。进程内集合仅管理正在等待的操作，不作为持久状态。此机制不承诺 Solver 进程崩溃后自动续跑。

网关生成请求 ID 和恢复链 ID；Runner 在下一次请求提交父请求引用。宿主校验父请求存在、确实失败且未恢复、链 ID 和会话一致、用途一致，随后剥离控制字段再交给提供方。错误反馈改变历史，所以 v2 不用内容 hash 推断恢复成功。成功只关联同链先前失败，其他会话或辅助请求不能清除故障。

SDK 的 `LlmFailure` 只保留声明字段。网关完整诊断在规范化之前写入会话投影，`agent/request-error` 按精确请求 ID 取回；不能假定任意自定义字段会被框架透传。内部 outcome 帧由 Runner 适配器消费，不交给模型或原生流累积器。

## 5. 证据、版本和交付

会话 `plugin:phyexp-request-recovery/*` 记录 `state`、`scheduled`、`started`、`stopped`、`healthy`，包含策略、动作、分类次数、合计次数、链 ID、请求 ID、等待及停止原因。宿主保留原始逐请求证据；`requestRecovery.failures` 附恢复链、父请求和 `recoveredBy`。最终 `failure` 对应实际终止请求，不把已恢复错误当作任务最终失败，也不把未恢复的错误因其他调用成功而清除。

组合加载回执包含实际启用策略及版本。配方、全部恢复源码进入执行资产、SDK profile 摘要及独立导出；只改策略配置也产生新的组合身份。默认配方为 `h0-sol-v3` / `h0-luna-v3`。旧冻结对象不修改、不热升级；新比较应重新冻结同一基础设施的基线与候选。

## 6. 验证要求

采用合成提供方和真实原生隔离 Runner 验证：混合故障、内容共享上限和合计上限、完整错误反馈、未完成流不执行工具、之前工具副作用不重复、原始工具注册也被校验、策略移除、取消/截止、压缩原子性、会话投影重建、请求关联和旧策略兼容。冻结与导出检查验证恢复源码和配置完整。

这些检查验证恢复机制，不证明真实模型的异常率或任务通过率改善。真实效果需对新冻结组合另做重复任务对照，保持模型、调用设置、任务时限和评分一致。
