# 插件版本管理与按需导出方案

2026-10-24 完整工程增量：新候选采用 `harness-composition-v3`。源码对象、隔离构建产物、构建输入回执、候选清单和最小可信适配器分别寻址；依赖/profile 的差异属于候选，适配器/任务/模型/资源属于外部条件。下文“框架不进入候选产物”和共享宿主 npm 装配只适用于 v2；v3 将候选运行依赖实际打入产物，不从平台 node_modules 加载生成代码。

v3 导出包含 `candidate/`、`candidate.tar`、`bundle.json`、`objects.json`、`recipe.json`、Python 精确锁和最小运行接入。`--verify` 与静态搬迁只核验身份；真实搬迁必须另外通过导出 run.py 执行官方任务，不能拿静态检查代替评分。独立包无需控制数据库、Meta 或工作台。

日期：2026-10-20 · 状态：Solver 存储、共享安装与按需导出已实现，通过离线、原生模拟供应商及实际 ZIP 搬迁检查；另提供显式历史去重与恢复工具。历史身份与研究记录保持不变，不自动整理开放活动。

执行 Harness 的持久成果由**插件版本和组合清单**构成。DeepSeek Harness 只记录准确版本及获取来源，安装时从对应发布包或 GitHub 提交获取；不在候选存储中另存框架副本。测试与导出根据同一清单装配，完整项目仅在运行或交付需要时生成。

本专题细化[需求第 7.1、7.7 节](../requirements/meta-harness.md)及[实现方案第 4、10 节](meta-harness-implementation.md)。实施顺序和验收由[开发任务书第 18 节](../plans/meta-harness-development.md#18-插件版本管理与按需导出)维护；已可使用的命令与备份要求以[运行说明](../operations/meta-harness.md)为准。

Meta 组合采用相同保存原则的新设计见[通用 Agent 方案第 10 节](meta-agent-and-evidence.md#10-版本身份存储与迁移)：复用内容对象及框架引用，工作区、会话和证据另存。该 Meta 增量已通过新 `meta-composition-v2` 实现，不能据此删除现有 `meta-composition-v1` 恢复资产；Solver 已实现的组合协议和导出边界保持不变。

## 1 版本与保存单位

| 对象 | 持久保存的内容 | 复用方式 |
|---|---|---|
| DeepSeek Harness 引用 | 获取来源、准确版本及相应的包完整性信息或提交标识 | 使用官方对应版本安装；不使用浮动分支或 `latest` 代替已选版本 |
| 插件版本 | 名称、版本号、源码、必要资产、入口、配置 schema、依赖声明和内容摘要 | 同一份内容只保存一次，多个候选共同引用 |
| 候选组合清单 | DeepSeek 引用、profile/必要 patch、选中的插件版本引用、启用配置、有效装配关系、固定 Solver 设置及依赖锁定信息 | 候选保存清单和摘要；公共锁文件等不变内容可以共享引用 |
| 实验与开发记录 | 父候选、变更说明、开发资料来源、平台版本、任务与环境、加载回执、评分、用量和报告 | 分别关联候选、Campaign 与 Trial；不复制进插件或默认导出包 |

组合清单优先沿用现有 Recipe，避免并行维护两份含义相同的配置。清单必须能够确定原生 profile/patch 的实际内容、插件作用域及有意义的加载顺序；原生服务依赖继续通过 Cordis 声明和解析。

插件版本号必须与确定的内容对应。名称、版本号和内容摘要共同定位已保存的实现，同名同号的新内容不能覆盖旧资产。修改插件代码生成新插件版本；只调整配置、增加或移除插件生成新组合，未修改的插件继续复用。

组合身份覆盖实际影响 Harness 行为的引用、配置和依赖锁定信息。时间、路径、人读名称、报告、纯开发资料修订及缓存位置不参与该身份。实验平台版本和任务镜像等比较条件另行记录与核对；组合相同不代表实验条件必然相同。

## 2 持久成果与安装缓存

框架安装、`node_modules`、语言虚拟环境、构建镜像和临时装配目录是按需准备的运行资源，不是每个候选必须拥有的独立副本。兼容的安装按锁文件及运行平台等实际输入复用，不能仅按 DeepSeek 版本判断全部依赖相同。共享安装对生成插件保持只读，临时会话和工作目录按 Trial 隔离。

缓存不存在时，根据已锁定的来源重建并核对内容；无法取得指定版本或校验不符时明确报告不可用，不回退到最新版。框架引用无需以完整源码快照作为有效性的前提。未发布的本地插件仍须保存代码与资产，不能仅记录工作区路径。

装配目录和导出目录不承担版本权威。缓存缺失或损坏时重建不会改变候选身份或插件源码；修复发布新目录，保留旧目录供在途进程使用。缓存释放必须避开在用资源，本次不提供自动清理。旧 Bundle、安装目录和镜像继续遵循原有恢复要求。

本次不引入远程插件仓库、新的存储服务或自动垃圾回收系统。先复用现有本地对象存储和记录能力，实现插件内容复用及共享依赖安装。证据、任务材料和开发资料的现有保存规则不因执行版本精简而取消。

## 3 从冻结到测试与导出

冻结时校验插件入口、资产、配置和依赖，保存新插件内容及不可变组合清单，再按清单准备隔离装配检查。已有插件版本和匹配安装直接复用，不复制整个 `src/execution/`、交付模板或依赖目录到每个候选。

测试和导出复用同一套解析、校验及原生装配规则。测试从清单解析准确版本，加载回执记录组合摘要、DeepSeek 身份、插件摘要、有效配置、工具和固定 Solver 设置；外部监督继续记录平台、环境及资源条件。草稿修改、缓存重建和宿主更新不能悄悄改变已选内容。

导出按已保存的引用收集插件，生成项目自己的依赖声明、锁定信息、原生启动配置和说明；框架及外部依赖由接收者按声明安装。仅收集选定版本及其实际依赖，不随包附带 DeepSeek 本体、安装缓存、未选插件或研究历史。不承诺离线安装。

导出清单绑定来源候选、组合摘要和导出工具版本，压缩包另有文件摘要。包装和安装路径可以变化；插件实现、有效配置及影响执行语义的入口必须保持一致。导出阶段不得重新选择依赖版本或让模型生成近似插件。若需要改变行为，应形成新候选并重新评价。

实际导出包仍须在原仓库及其数据、依赖目录不可访问的环境中安装和装配。内容检查、无真实模型的搬迁检查和真实独立运行分别记录，生成包不意味着已经完成全部验收。

## 4 现有外围代码的归属

现有执行目录混合了模型接入、隔离、工具传输和评测接入。实施前逐项记录调用者、职责、是否为该候选运行所必需、获取方式及验证方法，不以“公共运行支撑”作为整体复制该目录的理由。

| 职责 | 目标归属与交付要求 |
|---|---|
| 官方插件加载、Agent 循环、会话及工具扩展接口 | 复用所引用的 DeepSeek Harness 版本，通过原生配置和扩展点使用 |
| 本项目编写的策略、工具或模型接入插件 | 按插件版本保存；确为所选组合依赖时随包提供源码，或声明可获取的准确包版本 |
| 固定模型网关、认证、隔离及单次运行监督 | 先区分平台职责与独立运行所需职责；必要部分采用有明确版本的最小入口或适配包，说明为何需要及如何独立取得，不能只引用未发布的宿主文件 |
| Harbor 工具传输及任务执行适配 | 所选插件依赖其工具时，声明并验证所需适配；任务环境、qsim 和官方 verifier 作为明确的外部依赖，不默认附带整个评测平台 |
| Campaign 调度、跨实验预算、证据查询、报告和工作台 | 保留在平台，独立执行项目不依赖这些服务；研究记录单独关联或作为可选附件 |

必要的本地适配代码也按明确版本保存一次并被引用，不重新建立每个候选一份的完整运行底座。是否拆包以实际依赖为准，不要求把所有平台模块都改成插件。

存储调整不把固定模型、权限和资源约束交给产品内 Meta 或生成插件自行执行。独立交付仍须满足其声明的单次执行边界；依赖这些边界的旧行为在对应替代链路通过检查前不能删去，也不能将依赖缺失标成导出成功。

## 5 兼容与实施范围

新实现使用可区分的新候选格式；旧 Runtime Bundle 保持原件，通过兼容读取、校验和导出路径继续使用。新旧格式在查询、报告和版本选择中均能定位精确插件及来源，不能用当前草稿替代旧代码。

不自动转换进行中的活动，也不重算历史身份、评分、选择或报告。旧 Bundle 重复文件的释放属于独立的显式整理流程，须先证明引用完整、恢复与旧导出可用，并保留相应迁移记录。

经用户明确要求整理历史时，执行第 7 节的兼容去重流程；此授权不等于允许替换历史执行代码或中断正在运行的活动。

本次重构首先覆盖 Solver 候选存储、装配、依赖复用及导出。Meta 组合遵循插件版本与配置分离的原则，但现有 `meta-composition-v1` 的代码快照、宿主锁与镜像恢复机制保持当前协议；其存储迁移另行界定，避免同时改动停止审查和活动恢复。

实施依次完成：外围依赖归属核对、插件与清单契约、兼容读取、共享安装与测试装配、按需导出、查询及交付界面适配。具体自动完成条件见开发任务书第 18 节。运行说明中的可用功能和清理操作须在实现及相应检查完成后更新。

## 6 已落地格式与解析入口

新组合使用 `bundle.json` 的 `schemaVersion: 2`、`kind: plugin-composition`，契约见 [composition.schema.json](../../schemas/execution/composition.schema.json)。沿用 `bundleId` 作为数据库中的组合身份，新增解析及导出结果同时提供 `compositionId`；不重算旧 ID。候选目录只有 `bundle.json` 和规范化 `recipe.json`，人读名称、说明、时间及 KnowledgePack ID 留在开发/活动记录，不参与执行身份。

`objects/sha256/<摘要>/object.json` 描述一个插件、必要适配或依赖声明对象，正文在该目录的 `assets/`。相同内容只保存一次。组合引用这些对象及 DeepSeek 的准确 npm 包版本、下载地址和完整性摘要；当前版本从官方发布包安装，不另存 GitHub 源码副本。插件读取、材料查询、检查、执行及导出均使用 [manifest.py](../../src/execution/bundle/manifest.py)；Node 入口调用同一解析器，旧 v1 Bundle 仍按原文件清单校验。

必要适配的逐项交付清单位于 [assets.json](../../src/execution/assets.json) 的 `delivery`：组合校验、隔离原生宿主、固定模型与单次监督、Quantum-Harbor 桥接。各组记录职责和文件，启动模板及锁文件单独声明。构建器、未使用的旧 patch、平台控制服务和研究资料不进入新执行项目。必要适配按内容版本共享，不按候选复制。

共享安装由 [execution_cache.py](../../src/control/execution_cache.py) 准备。键覆盖锁文件、包声明、Node 版本、ABI、系统与架构；跨进程锁保护准备，完成校验后原子发布。适配缓存只包含所需固定代码及指向该安装的引用，运行时显式传入原组合；每个插件对象单独只读挂载进 Runner，会话和 Trial 输出各自隔离。

导出保留同一个 `bundle.json`，将引用的资产展开到项目内，并用 `objects.json` 保存对应内容描述。解析器核对所有声明、文件与配置，不依赖原存储。导出记录另存导出格式、导出器源码摘要及 ZIP 摘要。`delivery.json` 随包说明适配职责，`run.py`、`install-runner.mjs` 和锁文件提供原单次运行入口；不含 DeepSeek 安装本体或缓存。

## 7 已有历史的兼容去重

历史 v1 结果对应原代码及原 Bundle ID，不能把当前适配替换进去再宣称是同一个已测版本。显式迁移只调整物理存储：按原文件保存插件、历史适配、锁和框架引用，在 `objects/legacy-compositions/` 记录组合布局；跨适配版本相同的文件继续共享 `objects/blobs/` 内容。原候选目录保留硬链接兼容视图，文件内容、路径、摘要与身份不变。硬链接共享同一个物理文件，不额外保存源码副本，也不要求正在运行的后台升级读取协议。

历史适配对象使用 `legacy-execution-adapter` 类型，保留旧清单中全部已冻结文件；不套用新版本的交付允许列表来删除旧依赖。已有报告、评分、轨迹、数据库行、选择及历史 ZIP 不改写；新导出仍按原清单展开，保持原身份。新活动继续使用第 6 节的小型 v2 候选目录。

迁移仅纳入所有引用活动均已结束且无在途工作、无直接运行进程的 Bundle。一个对象只要仍被开放活动引用就排除。先生成计划与数据库快照，逐版本备份冻结文件并核对，再用原冻结检查代码和已有 Runner 镜像完成模拟供应商装配；不构建或替换共享镜像，不调用真实模型。通过后原子替换文件引用，将逐候选 `node_modules` 改为按原锁和当前平台验证的共享安装，最后删除隔离暂存的重复安装。

迁移日志记录准备、验证、替换、提交及释放阶段，同一计划可断点续做；源码可从独立校验的 ZIP 备份恢复为原文件。安装属于可重建缓存，恢复源码无需把重复依赖重新复制回来。缺失或损坏的共享安装在正常启动准备时按原锁重建。硬链接中的源码仍属于不可变对象，禁止就地编辑任何兼容视图；修改行为必须创建新版本。

工具入口、备份范围及恢复命令见[运行说明](../operations/meta-harness.md#显式整理历史存储)。跨活动去重不迁移 Meta 组合，也不删除研究记录。
