# Meta 自主资源规划与平台限额执行修改计划

日期：2026-10-20。状态：前两批修改与有限真实诊断已完成；检查记录及仍待处理的故障保存在本地开发目录。

用户决定目标和总体资源边界，Meta 在边界内自主安排实验，平台负责准确调度、计量和记录。此次增量将用户上限与 Meta 运行计划分开，减少固定策略造成的提前终止，并修复限额执行与故障归因的不一致。

本文面向平台开发者，承接[需求第 7 节](../requirements/meta-harness.md#7-运行控制持久记录与独立交付)和[实现方案](../design/meta-harness-implementation.md)。新活动绑定 `meta-resource-planning-v1`；无此标记的历史活动继续使用原有自动单次时限和收尾预留规则。具体接口见[Meta 资源规划资料](../../knowledge/plugin-sdk/guides/resource-planning.md)。

## 1 修改范围

首批修改集中于控制后台、Meta 工具、工作台和报告：区分配置来源，开放 Meta 计划调整，保存每批实验的实际条件，修复延时收尾计算。

请求等待、结构化拒绝原因传递涉及宿主网关，作为独立的后续增量。其修改范围须明确到宿主接口，不能把它描述成纯控制层改动。Quantum Harbor、官方任务与评分器、Solver 插件机制保持现有边界。正在运行进程的动态延期、动态 token 预留估计暂不纳入首批。

## 2 当前问题与对应改动

以下列出本次修改针对的原有行为及其影响。运行记录与离线复现保留在本地开发记录中。

| 当前行为 | 影响 | 对应改动 |
|---|---|---|
| [配置校验](../../src/control/store.py)将用户约束、自动预留和执行参数放在同一配置中；Meta 只能读取这些限制 | 难以判断参数是谁决定的，Meta 无法调整自己的资源分配 | 分开记录用户上限、Meta 计划及平台执行条件 |
| 单任务自动采用至多 1 小时；收尾自动预留总时长或 token 的一定比例 | 平台固定策略可能提前截断实验，预留也未必符合实际报告工作量 | 自动策略改为可见建议，由 Meta 提交实际计划；已有冻结配方约束明确展示 |
| [请求预算门](../../src/execution/host/budget.mjs)默认每请求预留 30 万 token，准入拒绝直接抛错 | 暂时被其他请求占用的额度可能导致任务终止 | 区分临时等待、余额不足及明确停止；首版不同时更换估算算法 |
| [任务领取](../../src/control/store.py)同时取延时截止和“活动截止减收尾预留”的最小值 | `drain` 的额外收尾时间被较早截止覆盖 | 分别计算新工作准入时间和已启动任务的执行截止 |
| 用户更新限额后，已启动 Trial、访问租约和工作进程仍保存旧值 | 界面显示的新额度不一定对当前任务生效 | 返回实际生效范围，明确展示仍使用旧条件的任务 |
| 请求准入发生在[网关请求记录](../../src/execution/host/model_gateway.mjs)之前，拒绝原因被缩减为 HTTP 状态 | 平台拒绝可能被误报为模型供应商错误，同时失败请求数为 0 | 单独记录准入过程，传递结构化原因 |
| [证据摘要](../../src/evidence/library.py)未投影请求恢复字段 | Meta 可能看不到原始归档已有的恢复事实 | 补齐 `failureContract` 和 `requestRecovery`，保留原始证据引用 |

平台当前允许 token、轮次和 Trial 总数为空值；这部分能力应保留。开发或诊断脚本自行增加的限制必须标明来源，不能因其进入活动配置就被认定为用户要求。

## 3 决策权限

| 类别 | 决定内容 | 可修改者 | 平台责任 |
|---|---|---|---|
| 用户上限 | 明确指定的活动总时间、token 软阈值、次数上限、并发上限及截止策略 | 用户 | 执行授权边界，记录每次变更 |
| Meta 运行计划 | 实际并发、批次时间分配、重复次数、收尾预留、阶段目标 | Meta；用户可覆盖 | 校验并执行，返回有效条件 |
| 平台执行条件 | 宿主容量、冻结配方上限、任务原有时限、连接保护和隔离规则 | 平台维护者 | 展示能力与限制，正确监督和清理 |
| 结果事实 | 用量、官方评分、错误、取消和恢复记录 | 由执行与审计产生 | 持久保存，提供统一查询 |

用户未指定的 token、轮次和次数上限使用真实空值。Meta 不能提高用户明确设置的上限，也不能改变固定 Solver 配置、官方评分或历史用量。

每项有效配置需要同时能追溯到决定者和数值来源。例如“Meta 采用平台建议”“开发代理覆盖诊断参数”和“用户明确设置”是不同来源。旧活动无法可靠识别来源时标记为历史来源未核实，不能自动归入用户指定。

总 token 的计量口径继续包含输入、输出及缓存相关用量，并展示分项。token 软阈值不表示已验证的金额或精确计费硬上限。

## 4 Meta 计划接口

`campaign_plan_update` 是独立于用户限额修改接口的受控操作。请求包含 `changes`、`reason`、`expectedPlanRevision` 和 `idempotencyKey`；下表前四个字段放在 `changes` 中并一起提交。工作台用户覆盖同一计划时使用 `POST /campaigns/{id}/plan`。

| 字段 | 含义 |
|---|---|
| `parallelism` | Meta 当前计划的实验并发数，受用户和宿主并发上限约束 |
| `defaultTrialTimeSeconds` | 后续实验默认分配的单次时长 |
| `closeoutReserveSeconds` | Meta 为分析、报告和收尾安排的时间，可设为 0 |
| `closeoutReserveTokens` | 有限 token 总额度内的计划预留，可设为 0；总量不限时不产生额外 token 截断 |
| `reason` | 本次计划或调整的理由 |
| `expectedPlanRevision` | 防止覆盖其他已生效调整的计划版本 |
| `idempotencyKey` | 保证重复提交不产生重复变更 |

阶段轮数和实验次数目标由 Meta 在理由或分析中跟踪；首版结构化计划仅接受上表前四个字段，不另设阶段次数截止。达到 Meta 的阶段目标后由 Meta 评估，不将其转换为活动额度耗尽。有限诊断使用调用者明确登记的次数边界，并保留其来源。

平台在一次事务中校验用户边界、保存计划版本及变更事件。响应包含已接受的值、实际生效范围、仍受旧条件约束的任务和限制来源。冲突或不可执行的设置明确拒绝，不静默裁剪。

Meta 可以调整自己的预留以继续探索，但不能通过增大预留、缩小计划时限或设置零剩余额度，绕过现有提前结束审查。由计划引起的暂缓调度应保持可恢复；即使次数边界已关闭新批次受理，只要活动仍可运行且有已受理任务，仍允许调整计划以调度和完成这些任务，不开放额外批次。活动结束仍遵循用户操作、真实资源边界或既有停止审查规则。计划变化进入审查快照，旧审批不能授权变更后的停止决定。

## 5 批次受理与实际执行条件

### 5.1 初始计划和基线

新策略下，Meta 在第一次实验批次受理前提交运行计划。现有自动 H0 批次应等待计划就绪，继续保留所选任务的基线覆盖要求。

平台将默认时长和预留建议作为上下文提供给 Meta，不先把建议转成不可调整的用户上限。Meta 自身的初始规划请求仍受用户总边界与平台模型请求保护约束。

关闭 Meta 的诊断或手动执行路径由调用者提供明确的运行计划，记录调用者来源；不从缺失字段推断用户要求了额外 token 或次数限制。

### 5.2 批次条件

扩展现有 `batch_submit`，允许批次明确指定单次时长，未指定时采用当前 Meta 计划。每个已受理批次保存计划版本、申请条件及可执行条件。重复次数继续使用现有字段，不另建一套计数系统。

任务启动时记录实际起止边界、剩余活动时间、用户限制版本以及冻结配方和任务约束。排队导致可获得时长变短时，先返回给 Meta 决定是否接受缩短条件，不能悄悄启动后视作原定条件完整执行。

已有 Bundle 的配方不能热修改。首次实现按真实冻结上限校验时间分配；超过冻结能力的设置明确报告不可执行。新冻结配方需要同步消除不必要的默认策略限制，沿用现有冻结和比较流程，并与 Quantum Harbor 原有任务时限分别记录。

单次时长包含启动、Solver、评分和清理。当前执行层已有的评分与清理预留为 330 秒，通过 `executionTimePolicy` 显式公开，区别于 Meta 的活动收尾计划。计划、批次与缩短确认不能分配不大于该预留的时长；排队后剩余时间不足也不启动。实际条件同时保存整次截止与 Solver 截止，启动开销仍会占用时间。此次公开并校验该约束，没有调整原有预留值。

### 5.3 修改生效范围

首版计划修改默认影响未来提交的批次。已受理批次保持其条件快照；尚未启动的任务只有经过显式调整并记录新条件后才采用新计划。已经启动的任务保持启动时条件。

用户提高总体额度时，界面和 API 应明确列出仍受旧进程上限约束的任务，不能声明活动内全部任务已扩容。用户收紧总体边界时，平台按新边界执行准入和停止策略，并记录对在途任务的影响；软 token 阈值不能保证撤回已经发生或正在计量的消耗。

### 5.4 严格截止和延时收尾

严格模式下，任务截止取用户活动结束时刻、任务获配时长及实际执行约束的较早者。Meta 收尾预留影响后续任务的启动安排，不追溯缩短已经受理任务的时限。

`drain` 模式分别保存停止启动新工作的时刻和用户允许的最迟结束时刻。后者包含明确配置的有限额外收尾时间；任务仍受自身有效时限约束。计算已启动任务截止时，不再混入更早的准入截止而抵消额外时间。

Meta 无权把严格结束上限自行改成启动截止，也不能增加用户允许的额外时长。界面分别显示上述时刻及预留用途。

## 6 请求准入与故障归因

后续宿主接口增量应使平台准入结果至少区分：

| 结果 | 行为 |
|---|---|
| 允许请求 | 建立唯一请求预留，再调用模型 |
| 暂时等待 | 其他在途请求占用可释放额度，等待结算后重新评估 |
| 剩余额度无法满足准入 | 保留计量与估算依据，通知 Meta；若等待已无意义，按明确预算原因结束对应调用 |
| 计划预留阻止继续分配 | 通知 Meta 可调整的计划因素，不伪装为用户额度耗尽 |
| 用户停止或截止 | 停止等待和新调用，记录对应原因 |
| 凭证、后台连接或账本异常 | 保留平台故障类别，不归入模型供应商故障 |

等待期间不调用模型，不计作额外模型重试，也不重复扣留 token。请求身份和预留必须幂等；取消、任务截止及后台重启后仍能结束或恢复等待。未知消耗继续保留，不能为了释放额度按零结算。

等待本地额度和接收模型响应是不同阶段。模型流空闲超时不应计入额度等待时间；账本连接有自己的有限超时与错误类别。具体等待实现须与现有 HTTP 超时、租约和取消机制一并验证。

第一版保留现有请求预留估算，先修复等待和归因。预留估算超过余额只证明当前策略无法准入，不能宣称已实际消耗完全部预算。后续再评估根据请求规模和历史用量改进估算。

所有拒绝须携带结构化类别、所属边界、计划或用户限制版本及可公开的依据。准入事件在网关正式调用记录之前独立持久化，统计分别展示尝试准入、等待、拒绝和实际模型请求。

## 7 证据与统计

Trial 需要关联用户限制版本、Meta 计划版本、批次申请条件、启动时有效条件、计划变更及最终停止原因。Meta、工作台、候选比较和报告从同一投影读取这些事实。

预算截断、Meta 主动停止、官方未通过和模型连接故障应分别解释。官方未评分继续保留空值；已获得足额任务时限后的失败遵循活动绑定的任务完成规则。新增原因如果改变现有规则的类别或分母，需明确版本化，不能顺带重算历史活动。

时间分配、执行条件或基础设施不同的结果必须显示比较差异。Meta 可分析资源与性能的取舍，但不能把增加运行时间造成的差异直接归为插件效果。

证据摘要补齐最终故障契约与请求恢复字段，避免把成功恢复隐藏在仅原始归档可见的记录中。原始评分、归档和历史统计快照保持原样。

## 8 分阶段实施

| 阶段 | 主要改动 | 完成范围 |
|---|---|---|
| 第一批 控制与规划 | 配置来源、用户上限与 Meta 计划分离、计划接口、初始计划与基线衔接、批次条件快照、`drain` 计算、有效条件展示 | Meta 能规划后续实验，平台准确返回可执行条件；不宣称准入等待已修复 |
| 第二批 准入与诊断 | 宿主结构化错误、准入审计、临时等待、停止分类及恢复字段投影 | 临时预留不足不直接结束任务，平台拒绝不再冒充供应商错误 |
| 后续可选 | 动态预留估计、已启动进程的协调扩容 | 单独评估，不作为前两批的隐含依赖 |

主要入口为 `src/control/store.py`、`service.py`、`meta_context.py`、Meta 工具包、共享工作台客户端及契约；证据和报告使用已有统一入口。第二批额外涉及宿主预算门、网关和最终失败诊断。

实施时同步更新[需求](../requirements/meta-harness.md)、[实现方案](../design/meta-harness-implementation.md)、[运行说明](../operations/meta-harness.md)、契约和 SDK 资料源。协议、工具及策略版本以最终实现为准，不用文档草案名称冒充已发布接口。

新活动显式绑定新的规划策略和 `task-completion-v3`。v3 延续 v2，并为预算准入不足及平台账本、凭证错误增加明确类别；原有科学结果、模型故障和足额单次超时规则保持。旧活动保留原配置和行为，不批量迁移；旧配置来源不明时展示为未核实。后台重启恢复已保存计划和受理快照，不重新套用最新默认值。执行接口变化仅随新冻结 Bundle 生效，比较必须使用相容的基础设施。

## 9 验收条件

优先使用隔离账本、可控时钟和假模型适配器验证，再运行受影响的单元、契约与界面检查。下列场景均不得依赖真实模型随机行为：

| 场景 | 预期 |
|---|---|
| 用户未设置 token 或次数上限 | 不生成隐藏上限；实际和未知用量继续记录 |
| Meta 修改自己的计划 | 变更有理由和版本；不提高用户上限 |
| Meta 达到阶段次数目标或增大预留 | 通知评估或暂缓调度，不能绕过结束审查 |
| 初始计划尚未提交 | 不以平台隐藏默认值启动基线；规划调用仍受总边界约束 |
| 并发请求暂时占满预留 | 等待结算后可继续，模型调用及记账不重复 |
| token 总额度不足或未知消耗阻止准入 | 显示实际依据，不误报供应商错误，不清零未知消耗 |
| 等待中取消、到期或后台重启 | 取消或恢复行为可追溯，无泄漏预留和重复请求 |
| `drain` 配置额外时长 | 允许范围内的任务截止不被准入截止覆盖 |
| 用户提高总体时限或 token 上限 | 返回未获同步扩容的现有任务，界面与执行一致 |
| 计划修改与已受理或运行任务并存 | 旧快照保持，显式变更有记录；不静默替换条件 |
| 预算、租约或账本错误发生在模型调用前 | 存在准入事件，原因归属平台或资源边界 |
| 请求恢复后获得结果 | Meta 摘要可见恢复事实，最终成功不带未恢复故障 |
| 不同资源分配参与候选比较 | 差异可见，官方空值和原始评分保持 |
| 旧活动重新打开或服务重启 | 不改变历史行为、评分规则和原始证据 |

只修改文档时检查内容、链接和规则一致性。后续真实验证沿用当时已有授权，运行前保存与参考条件的差异及每项限制来源；开发代理不得把自行选择的上限标记为用户要求。需要控制测试规模时，优先采用明确的任务集合和重复次数，不悄悄添加会截断单次执行的资源上限。
