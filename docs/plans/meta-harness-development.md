## 1. 执行目标与角色

你负责将当前 H0 项目实现为满足需求 v0.12 的可用系统：Meta 能使用通用 Agent 能力自主开发执行插件、组合测试、读取完整证据并生成报告；用户能在 DeepSeek Harness 原生工作台中操作；选定候选能导出并独立运行。Meta 插件组合、停止审查与可比较性基础见第 16 节；执行插件版本存储、依赖复用及按需导出见第 18 节；通用 Agent、持久工作区、完整文件与恢复见第 19 节。按当前用户授权范围推进，文档更新本身不启动代码重构、历史清理或真实实验。

本文直接面向执行开发的 Codex。M0–M5 是工作包和技术完成条件，不是等待人审批的阶段。通过检查后自行进入下一个可执行工作包，直到形成需要用户判断的成品，或遇到确实无法独立解决的外部依赖。

区分三个角色：**Codex / GPT-6 Astra 是实现本项目的开发代理；产品运行时的 Meta 模型和 Solver 由用户另行配置。** 不因开发使用 Astra 就自动修改运行时模型。本文规定软件开发的推进方式，不规定产品内 Meta 模型如何寻找更好的 Harness。

不按人日或周数安排开发，也不把人类工期按某个倍数压缩为 AI 工期。以可验证产物、自动检查结果和用户尚需判断的问题衡量进度；记录实际运行耗时与消耗，不用预测速度替代完成证据。

## 2. 自主执行规则

1. **先读取现状，再继续工作。** 从根目录 `AGENTS.md` 进入，读取需求、实现方案、已有进度记录与相关代码。保留用户改动、历史实验和原始证据；不要因为进入新工作包就重做已有有效成果。用户只请求修改文档或局部工作时，按当次范围执行，不因读取本任务书自动启动全部实施。
2. **自行处理工程选择。** 按实现方案第 3 节的目标目录和依赖边界落实代码；内部文件布局、接口细化、组件拆分、测试实现和范围内的错误修复由你决定。方案细节可按验证结果调整并记录原因；固定 Solver、权限、预算、证据边界、原生 UI 优先和独立导出要求不能自行削弱。不为目录迁移增加人工确认。
3. **连续推进到可体验结果。** M0、M1、M2 的检查通过后直接继续。M3 和 M4a 交叉完成最小真实闭环。不要在只有接口草稿、骨架、测试夹具或静态页面时请求用户验收。
4. **验证由你完成。** 运行与改动相关的契约、集成、故障和 UI 检查，定位并修复失败。已有检查通过且相关内容未变化时复用证据；不为阶段换名重复跑模型，也不以少测或隐藏失败来加速。
5. **先实现完整的小流程，再扩展覆盖。** 可以交叉推进无依赖的工作，不要求按文件顺序逐项施工。不要先堆满全部空接口；但工程样例跑通不代表隔离、额度或真实接入已经验证。
6. **真实调用遵循已有授权。** 先查已有模型配置、实验范围和预算。已有有效授权就直接按计划执行；缺失时先准备具体的最小运行计划，列明模型、任务、批次/Trial 数、时间与用量上限、收尾预留，再集中请求缺失信息。等待期间继续不依赖这些信息的工作，不重复请求已经授予的权限。
7. **保留真实实验成本。** 基线、插件候选、重试和导出验收均记账；已验证且条件仍匹配的基线可以复用并标明来源。不得用换工作包、换会话或故障恢复获得免费补跑。
8. **只有明确问题才找用户。** 可自行修复的代码、测试或 SDK 接入问题不构成人工验收。确需用户输入的情况见第 3.4 节；说明证据、已尝试的处理和需要决定的最小事项，继续其他工作。
9. **保存可续接进度。** 每个有意义的里程碑更新第 11 节的状态与证据。上下文切换或会话结束不等于项目完成，下次从未完成项继续。
10. **按实际覆盖声明完成。** 模拟测试、真实模型实验、官方评分、独立运行验收和用户验收分别记录。科学零分可以是有效负结果；未运行、未评分、未验证不能写成通过。

当前已有离线检查入口为 `npm test`；真实入口 `npm run h0` 会调用模型和实验环境。新增检查入口由你实现并记录实际命令，不将本文中的接口名称当作现成可调用工具。

## 3. 推进路线与人工验收点

### 3.1 工作包与自动推进

| 工作包 | 必须产出 | 完成后的动作 |
|---|---|---|
| M0 关键契约验证 | 目录迁移映射与依赖检查、SDK/隔离/网关检查、两个插件的最小接入、匹配执行版本的开发资料与查询 | 自检通过，直接进入 M1，不请求人工架构验收 |
| M1 冻结执行与导出 | 主要代码迁移与旧入口回归、从确定版本实际装配的 H0/样例插件、可搬迁的插件项目与声明依赖；存储重构见第 18 节 | 自检通过，直接进入 M2，不请求人工目录验收 |
| M2 后台运行控制 | 持久调度、额度、监督、恢复、部分失败归档；已获授权的最小真实 H0 接入证据 | 继续 M3 与 M4a；缺外部资源只阻塞对应真实检查 |
| M3 Meta 四类能力 | 真实代码开发、组合测试、受控证据、每轮/最终报告、恢复 | 与 M4a 共同满足人工验收 A 的准备条件 |
| M4a 最小可用工作台 | 原生 UI 中的一条完整用户路径，接真实后台和真实结果 | 提交人工验收 A；等待时继续不依赖体验反馈的工程工作 |
| M4b 工作台完善 | 根据 A 的反馈修正交互/报告，补齐比较、异常、生命周期与导出视图 | 与 M5 一起完成交付 |
| M5 完整技术交付 | 故障覆盖、完整示例、实际导出包搬迁执行及安装恢复说明 | 所有技术证据就绪后提交人工验收 B |

默认路线：**AI 连续完成 M0 → M1 → M2 → M3 + M4a → 人工验收 A → M4b + M5 → 人工验收 B。**

人工验收 A 要求 M3 与 M4a 中支撑最小真实路径的子任务完成；完整异常覆盖等后续任务保留为未完成，在 B 前补齐。不能因为 A 已就绪就把整个工作包提前标记为通过。

M0–M5 的编号保留工程依赖与追溯用途，不能据此每完成一包就结束工作。两个计划内人工验收点聚焦人的使用判断，不把技术测试交给用户。如果用户已明确验收等效内容或明确要求跳过某次中间验收，记录并沿用该决定，不重复索要确认。

### 3.2 人工验收 A：最小真实闭环是否好用、看得懂

**何时提交：** M0–M2 的相关检查通过，M3 的最小真实闭环与 M4a 已完成。你已自行完成演示流程、修复已知阻断问题，用户可以直接打开原生工作台查看成品。

提交前必须准备：

- 一个已完成的受控真实 Campaign：包含可比 H0 证据、Meta 实际生成或修改的插件、候选测试、官方评分、每轮分析和最终简报。可复用条件匹配的基线，不要求分数提升。
- 可操作的原生工作台：配置入口、活动状态与消耗、暂停/恢复/停止入口、候选/报告阅读、证据定位和导出入口已接通。故障或暂停演示可用明确标注的受控测试活动，不冒充真实科学实验。
- 实际导出目录或压缩包，至少已通过内容和搬迁装配检查；真实独立运行状态如实显示，完整验收可在 M5 完成。
- 一个简短验收包：启动/打开方式、建议查看顺序、真实与模拟数据标识、已知限制，以及本次需要用户判断的两三个问题。

**请用户判断的内容：** 操作是否顺手；报告是否能让他理解“改了什么、发生了什么、为什么保留或放弃”；默认展示和配置是否符合他的工作习惯。不要要求用户阅读源码、核算账本或替你验证隔离。

**为何需要人：** 技术检查不能替用户决定工作台是否便于使用、报告是否表达了他关心的内容。让用户在整体完成前体验，避免在错误的交互方向上继续细化。

**提交后的动作：** 等待有关体验方向的反馈，不将沉默当作通过；同时继续不依赖反馈的故障测试、依赖检查、恢复验证与文档工作，不中断在途监督。修正用户指出的问题并验证；若涉及必须由用户重新判断的体验变化，再展示对应改动，不重走所有已通过的技术检查。

### 3.3 人工验收 B：完整版本是否可交付

**何时提交：** A 的反馈已落实，M4b/M5 完成，需求验收矩阵已由 AI 执行并附证据。实际导出包已在原仓库不可访问的环境中，使用声明依赖和外部配置完成约定执行及官方评分链路。

提交前必须准备：

- 可安装、启动和恢复的工作台套件与独立后台；安装说明由你在干净环境按步骤验证。
- 一个真实、可追溯的最终总报告，链接到候选、各轮报告和证据，展示实际消耗、停止原因、失败分支及泛化限制。
- 实际独立执行项目、内容指纹、安装启动说明和真实搬迁验收记录；包与被验证的候选身份一致。
- AI 技术检查清单、未解决问题及影响范围。必须项有缺口时，交付状态为未完成，不能把它包装成人工签字即可通过的版本。

**请用户判断的内容：** 这套操作与报告是否已经满足日常使用；最终执行项目是否符合他希望取得和维护的交付形式；剩余非阻断限制是否可以接受。用户可按兴趣试用，但不需要重新执行你的完整测试集。

**提交后的动作：** 按反馈修复并更新相关证据；用户明确接受后记录完成。等待反馈期间可以继续已授权的收尾，不擅自开启更大规模的进化实验、发布或新功能。

### 3.4 计划外需要用户的情况

只在以下事实已经出现、且现有授权/资料不能解决时请求输入：

- 缺少实际运行所需的模型选择、认证、外部环境访问或预算。此时需要的是资源/配置输入，不是提前验收未完成系统。
- 验证证明关键方案无法满足需求，剩余可行路线会改变产品范围或既定边界。带具体失败证据、可行替代和影响让用户决定；范围内的实现调整自行完成。
- 用户需求之间存在无法同时满足的冲突，或新增工作超出已授权范围。

不要因预计耗时、工作包结束、普通测试失败或代码需要重构而停下开发、转向请求人工批准。也不要因需要一项输入就放弃仍可推进的其他部分。

## 4. M0 契约与技术验证

### 执行任务

- **M0-1 固定兼容基线。** 记录 dsh 0.2.1-rc.2、H0 配方、实际工具 schema/提示、Harbor 与镜像身份；保留既有离线测试，不改写历史实验。
- **M0-2 验证 Cordis 插件扩展面。** 用不含科学策略的技术夹具验证工具注册、合法结果处理、公开上下文扩展、生命周期和移除依赖行为；记录支持与不支持的 API。为 `packages/meta-harness/` 建立最小可加载包，以假后台验证受限客户端入口；完整业务工具在 M3 实现，技术夹具不冒充科学插件。

- **M0-5 定稿最小数据契约。** Campaign、KnowledgePack、PluginVersion、Candidate、Batch、Trial、Usage、Evidence、Report、Export 使用有版本 schema；建立正常、失败、未评分、未知用量及资料版本不匹配样例。

- **M0-7 验证插件开发资料和只读查询。** 针对锁定的执行 SDK/profile 生成一份带来源与指纹的资料包，提供简短说明、文档/类型索引和通过检查的技术样例。验证 `sdk.search/read/inspect` 的契约及原生 `cordis_inspect_list`、`cordis_inspect_query` 的受限接入，覆盖目标版本匹配、缺失接口、开发宿主特有服务过滤、敏感配置过滤和浏览器离线。查询不得执行业务方法、修改 profile 或绕过候选检查，样例不规定科学改进流程。
- **M0-8 确定目录迁移与依赖契约。** 按实现方案第 3 节记录旧路径→新职责、保留的命令/导入入口、根目录推导与配置引用、Node/Python 依赖、测试及源码指纹覆盖范围。明确两个插件的包入口与锁定安装方式、执行资产和平台资产的清单边界、仓库外数据目录；不要求全仓改成发布包。建立可复跑的依赖检查入口，用合法/非法夹具验证能发现执行代码直接或间接导入平台、插件越过 API 访问后台实现、执行配置指向工作台等问题；动态加载项需显式清单，不能仅按文件夹存在判定合格。检查可先报告待迁移旧代码，在 M1 结束前清除新实现的违规，不采用全局忽略掩盖问题。保持根 `AGENTS.md` 为简短导航和约束入口，完整映射与实施进度写入第 11 节记录。

### AI 自动完成条件

通过可控夹具检查协议、计量和权限边界，不调用真实模型；夹具无法访问真实认证文件、控制数据库、隐藏任务或其他活动。模型循环仍属于 dsh。通过后确定容器通信、网关、客户端构建和资料查询方案，再进入 M1。

目录映射覆盖全部现有执行代码和关键路径引用，两个插件的包入口已按目标目录完成最小加载检查，依赖检查能拒绝约定的违规夹具。`npm test` 仍通过；M0 不要求尚属 M1 的完整迁移或依赖闭包已经完成，待迁移项必须有明确去向。

M0 必须同时交付两个可复查结果：工作台插件能在锁定 dsh 版本中加载、切换、卸载和重连，独立监督夹具不受影响；Meta 可在无浏览器情况下读取目标执行版本的资料/API，资料不符或接口不可用时收到明确诊断。M0 验证接入与生命周期契约，完整后台的持久恢复和额度执行仍在 M2/M4 验收，不能提前标记已实现。

原生 UI 接入若存在阻碍，先记录具体缺失接口并调整插件接入设计；独立 Web 外壳是后续可选方案，不默认同时开发两套界面。资料接口不能以直接暴露整个 UI/控制宿主注册表作为替代。

若现有订阅流式接口外移不可行，先评估兼容接入适配，保持固定模型、凭据隔离与原始计量要求；不能以继续在宿主机加载生成插件作为临时正式方案。真实 provider 的最小兼容确认安排到 M2 的受控测试中。

**完成证据：** 目录/依赖迁移映射、兼容与资产清单、离线基线结果、依赖检查的正反例；SDK/两个插件包的加载检查、网关与隔离测试结果、原生 UI 生命周期记录、资料包清单/摘要、版本不符和权限过滤的检查结果。保存真实命令、结果和产物位置；接口草案或仅编译通过不能替代这些证据。

**下一步：** 自检通过后直接进入 M1，并复用 UI/资料查询原型。只有剩余路线需要改变需求时才按第 3.4 节请求用户决定。

## 5. M1 冻结执行项目与最小导出

## 16. Meta 插件组合与停止审查增量

状态：首期代码已落地，按以下条目持续验收。设计见[Meta Harness 插件组合设计](../design/meta-harness-composition.md)，产品规则见需求第 2.2、2.4、2.5、6.3、7.4.1 节。本节是后续实施与验收依据；撰写或阅读设计文档不自动启动代码改动、活动迁移或真实模型实验。

### 实施工作

1. **分离能力并验证原生组合。** 在现有 Meta 安装包内分离活动服务、查询工具和操作工具；用原生预设声明 Meta 与审查者，补充所需宿主服务。各插件说明接口、依赖、配置、关闭行为及合法替换或基线，组合校验识别缺失依赖与冲突。复用原生 Subagent 后端，不新建 Agent 循环、插件管理器或活动账本。
2. **迁移角色和作用域。** 将完整 system 覆盖改为可组合片段，保留用户目标的字面量语义、模板摘要和固定 Solver 约束。审查者显式选择只读预设，后台验证真实身份，禁止继承写工具或递归委派；逐 Agent 状态与清理归属明确。
3. **实现停止申请和受管审查。** 区分三类停止条件，绑定版本化策略及申请证据。通过原生子会话取得结构化审查结果，固定宿主核验归属，后台持久保存并核验适用性；主 Meta 不能自行伪造批准。审查拒绝、证据不足和技术失败分别处理。
4. **贯通续接、预算和恢复。** 审查与主 Meta 共用原有预留、截止和计量；取消覆盖已发布激活，重复申请不重启子会话。拒绝后可继续探索，普通回合结束不关闭活动，等待实验不空转。重启先对账和恢复消费位置，缺失组合或审查服务时不退回旧结束行为。
5. **记录组合并呈现事实。** 冻结精确组合配置与资产，记录父版本、差异及实际加载回执，恢复不依赖同名预设的最新版本。Campaign 关联组合、模型、初始执行候选、任务与材料范围、限额、最终候选及真实结果。按插件关联加载、触发、降级和失败，可靠归属成本，未知信息不猜测。工作台与报告读取同一审查记录，区分审查通过、目标达成、资源停止、故障及未完成项；任务成功率共用活动绑定的 task-completion-v1/v2/v3/v4，新活动采用 v4，历史活动不重算。
6. **保护迁移与导出边界。** 新契约绑定新活动或明确的配置修订，不回写旧目标、结束理由、评分、选择或报告，不自行重开已结束活动。Solver 和独立执行包不加载 Meta 审查能力；实施后才更新运行说明中的可用功能。

5. **实现按需导出并适配查询。** 从原组合收集插件、配置、锁及必要适配，复用测试的解析装配逻辑。更新候选差异、源码浏览、报告引用及交付入口；包摘要与组合身份分开，安装说明匹配实际依赖。原 Bundle 保留旧导出逻辑。

### 实施顺序

### 完成条件与验证范围

完整矩阵以[专项设计第 12 节](../design/meta-agent-and-evidence.md#12-验收矩阵)为准，以下闭环必须全部形成证据：

- **六个原生插件可独立验证。** 分别检查服务/工具 schema、直接依赖、错误传播、卸载及合法替换；缺少提供者、重复工具、错误角色或不兼容结束申请契约应被发现。主 Meta、研究子代理和隔离审查者只得到各自能力；业务插件不互相调用模型工具。关闭审查不绕过结束门槛，卸载插件不撤销已受理 Trial，移除全部 Meta 插件后通用 Agent 仍可读写文件和使用终端。
- **独立调查和开发。** 使用本地脚本 provider 与真实原生 Agent，从目录找到失败 Trial 的完整评分及轨迹，执行 Python 分析、编辑插件、检查并冻结，提交一次实验，收集官方结果并继续处理通知。不能由测试宿主提前将关键诊断塞入上下文。
- **长输出不丢失。** 覆盖旧 16 KB 输出和 500 文件边界、原生工具自己的裁剪、超时/失败/取消、磁盘容量不足；验证末尾标记、来源摘要和明确的完整性状态。只保存裁剪后文本不算通过。
- **权限和委派真实有效。** 主/子代理文件范围、共享预算、取消和并发修改得到验证；终端不能取得审查身份或修改官方材料；停止审查独立通道不能被主 Meta 冒充。
- **恢复不丢通知、不重复副作用。** 注入响应中断、业务受理后响应丢失、持久化与确认之间崩溃、后台和 Runner 重启及并发恢复。核对同一 Batch/Trial、操作记录、用量与故障链，覆盖恢复耗尽和到期场景。
- **历史与成果保存一致。** 旧评分、归档、分析、选择与导出摘要不变；新增路径是有来源的新视图。新组合不保存框架副本，不把分析、日志、会话或研究子代理带入 Solver 与导出。
