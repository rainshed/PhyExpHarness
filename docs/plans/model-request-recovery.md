# 模型请求恢复与任务失败计分修改计划

初版：2026-10-19；新基线增量：2026-10-23。第 1–6 节记录原请求恢复边界与计分增量；当前 H0 默认策略以第 7 节为准。

## 1. 目标与边界

过载或连接中断只结束当前模型请求，不能永久封锁同一任务的后续合法请求。执行插件可以在 DeepSeek Harness 原生失败步骤接口选择恢复；初版 Solver 默认不自动重试，也不自动重跑整个 Trial；2026-10-23 的新 H0 v2 增量见第 7 节。

新 Meta 自身的技术恢复、持久工作区与通知对账另见[通用 Agent 设计第 9 节](../design/meta-agent-and-evidence.md#9-会话持久化与恢复)，已独立实施。它不改变 Solver 冻结策略和评分版本；不能以单请求重试代替主 Meta 的会话恢复。

任务最终因模型服务过载、连接中断或响应连接不完整结束且没有官方评分时，派生任务完成分计 0，进入成功率分母；官方 null 保留。已恢复请求不作为任务终止原因。预算、截止、用户取消、固定模型和工具边界继续由外部宿主执行。

本次不开放网关源码给产品内 Meta，不改变 Quantum Harbor，不新增真实模型实验。其他未评分原因沿用现有规则；异常流保护仍终止不安全请求，不能执行截断工具参数。

## 2. 请求与任务状态

网关分别保存逐请求失败历史、必须停止的终止状态和最终任务诊断。过载、传输错误及无完整结束回执允许后续请求；其余现有保护终止规则保持。每次调用使用新的请求 ID，独立预留和结算；未知用量不能按零结算。全局取消后不再接受调用。

结构化错误包含安全的错误类别、网关请求 ID、可用的 HTTP 状态和 Retry-After。原始错误留在审计记录中，未知提供方错误不一概归类为过载。跨进程传输保持错误类别，使原生 agent/request-error 扩展点可供执行插件使用。

恢复重跑失败模型步骤，保留已完成工具结果。失败的部分输出保存在证据中，不进入下一次有效模型历史。通过相同会话和请求内容关联恢复记录，其他请求成功不清除尚未恢复的故障。最终诊断优先使用终止步骤的请求 ID，避免把最早错误冒充最终原因。

执行器、Meta 通道和诊断读取器同步采用新契约；历史归档继续按旧契约读取。已恢复故障显示为请求历史，最终任务成功时不挂载历史失败原因。

## 3. 统一计分

本增量引入 task-completion-v2，下表记录其历史故障计分规则；资源规划随后引入 v3。当前新活动规则以[任务完成规则 v4](../design/task-completion-v4.md)及需求第 3.3 节为准。已有活动保留原绑定版本，缺少字段按 v1 读取；历史评分、报告和选择快照不改写。

| 最终情况 | v2 派生任务完成分 | 官方评分 |
|---|---|---|
| 官方通过，包括恢复后通过 | 1 | 保留 1 |
| 官方未通过，包括恢复后未通过 | 0 | 保留原值 |
| 已结束，过载或连接故障导致无评分 | 0 | 保留 null |
| 正在运行或恢复 | 待定 | 保留原值 |
| 用户取消、环境或评分器故障、待归因 | 沿用原规则 | 保留原值 |

故障原因和计分结果分开：连接故障仍有外部原因，但在 v2/v3 中其终止任务计 0。不能将笼统的 model_response_error 全部判为该类故障；以明确的规范化故障类别或受信诊断字段识别。

后台 outcomes 是唯一计算入口。工作台、报告、Meta 上下文、候选选择和停止审查读取同一活动版本。快照复用必须匹配规则版本。旧结果按新规则重算属于另行明确标注的统计投影，本次不自动迁移。

## 4. 实施顺序

1. 修改网关与进程桥：拆分失败状态，传递结构化错误，保持默认零次自动重试和固定宿主约束。
2. 修改执行器及故障诊断：保存请求恢复历史和最终失败，兼容旧文件，防止成功任务被历史错误污染。
3. 保留本增量引入的 v2 与共享投影，当前新活动按资源规划契约绑定 v3；同步契约、界面文案及 Meta 的规则说明，旧活动保持原绑定版本。
4. 补充失败步骤插件资料和只读类型查询；以隔离环境中的测试插件验证真实原生恢复链路。
5. 完成相关离线测试、构建、边界检查，并在本地开发记录保存检查结果。

## 5. 验收

- 过载后可以发起第二次合法请求；默认无恢复插件时只调用一次。
- 输出中途断线后，测试插件重试成功；失败的部分参数不执行，之前的工具副作用不重复执行。
- 所有请求逐次记账，失败用量未知仍保留；预算拒绝、截止和用户取消不能被恢复插件绕过。
- 并发或不同会话的请求记录不互相清除；最终故障对应实际终止步骤。
- 恢复成功不被第一次失败污染；最终未恢复的模型过载或连接故障在 v2/v3 计 0，v1 保持原口径；v3 的预算准入与平台故障分母规则按资源规划计划另行验证。
- 官方评分优先于后续清理错误；待运行、取消、评分器失败等保持原语义。
- 工作台 API、报告、Meta 查询和选择快照的分子、分母、规则版本一致；原始记录不变。

新网关随新冻结 Bundle 生效。旧 Bundle 内容及基础设施摘要不变；后续效果对比应使用同一基础设施版本重新准备基线与候选。

## 6. 连接诊断补充

受信模型网关增加 `model-transport-v1` 诊断，覆盖 Node 原生 WebSocket/Undici 的请求与连接关联、复用、协议阶段、关闭及错误原因、SSE 回退。诊断从传输层观察适配器过滤前的事件；已安装的 Pi 适配器不透传 `start` 和完整诊断对象，因此不能只依赖其内容流判断连接阶段。脱敏审计保留错误原因，公开故障摘要只保留结构化事实。观测缺失保持未知，不改变执行策略。

计分延续 v2/v3：最终未恢复的连接失败为任务完成分 0，官方 `null` 保留；恢复成功采用最终官方结果。补齐 `WebSocket closed` 等明确传输错误的识别，避免正常携带关闭码的失败漏入泛化的 `model_response_error`。不重算旧活动。

验证覆盖响应开始前断开并回退、开始后无正文断开、显式恢复成功及恢复耗尽、关闭码、并发连接与复用关联、脱敏、官方空值保留和跨入口计分一致性。测试使用回环协议服务及虚构凭据，原始真实日志只留本地。

## 7. 新 H0 v2 的固定请求恢复

`recipes/h0-sol.json` 和 `recipes/h0-luna.json` 默认绑定 `solver-request-recovery-v1`，`retryDelaysSeconds=[2,5,20,30,60]`。这项通用能力属于固定执行基础设施，H0 与同一活动的候选共同使用；不计入 Meta 研发插件。配方与实现都进入组合摘要、SDK profile 身份和独立导出；缺少该配置的历史配方不启用恢复，旧冻结对象不改写。

- 仅恢复网关确认的连接失败、流中断/不完整及明确过载。每个失败模型步骤最多追加五次请求，成功后的新步骤重新计数；不重跑整个 Trial，不重复已经完成的工具副作用。
- 主循环通过原生 `agent/request-error` 恢复。上下文压缩使用相同策略恢复当前摘要请求，成功完整接收后才提交摘要；失败部分内容和用量块不拼入新摘要，所有实际调用仍由宿主独立计量。
- 等待时间取本档间隔与有效服务端 Retry-After 的较大值；等候将触及原截止时间时直接停止。等待可被用户取消或插件卸载中断。预算、认证、固定模型和流保护保持原约束，未知用量不清零。
- 提供方通用重试保持零次；内置恢复接管可恢复请求直到耗尽，随后不转交候选恢复监听器追加同一链。插件自行发起的普通 `ctx.llm.stream` 调用仍由调用方处理，只有 `purpose=compaction` 走内置摘要恢复。
- `plugin:phyexp-request-recovery/scheduled`、`started`、`stopped` 记录档位、等待、失败请求 ID 与停止原因；计数由会话投影恢复。网关原始审计和最终失败契约不变。此能力不承诺进程崩溃后自动续跑 Solver。

验收采用离线提供方和真实隔离 Runner：完整五档耗尽（六次调用）、同一步递增/新步骤复位、连接前失败与中途断线、缺少结束回执、压缩恢复、已完成工具不重放、部分参数/摘要不泄漏、取消与截止停止、预算再次准入失败、认证不重试、逐请求记账及未知用量保留；另检查冻结导出身份与旧配方零重试。没有新增真实模型实验，也不更改活动评分版本。
