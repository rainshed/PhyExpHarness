# Meta-Harness 需求文档

版本：0.15 · 日期：2026-10-23 · 状态：需求基线；参考实验新增 Claude Code、UI 独立开关与用户选定范围内的 Meta 自主组合，设计与开发计划已编写，功能尚未实施。进化可读性、插件版本管理与按需导出已实现；Meta 通用 Agent 核心链路已实现、完整验收继续，Meta 组合效果比较仅保留设计基础。已有能力与限制见[运行说明](../operations/meta-harness.md)，具体验收证据保存在本地

本文依据[项目设计哲学](../design/design-philosophy.md)，规定 Meta-Harness 的核心能力、实验边界和交付要求，供 PhyExpHarness 实施与验收使用。“必须”表示验收要求，“建议”表示可调整的实现选择。工具名称、存储格式和界面布局由实现阶段确定。

用户必须能够永久删除单次进化活动及其全部所属历史、会话、实验、证据、报告和平台导出。运行中的活动先停止所有所属工作，再清理；失败可续做，全部完成后才视为删除成功。其他活动显式纳入其历史时阻止删除，共享执行资产按剩余引用保留。仅用户可授权，Meta 不可删除历史；用户明确删除是日常证据保留规则的例外。范围、恢复及验收见[活动删除设计](../design/campaign-deletion.md)。

## 1. 目标与设计原则

Meta-Harness 在给定任务范围、固定 Solver 及其模型和调用设置的情况下，帮助用户选择的开发模型寻找更有效、稳定且可复用的执行 Harness。提高任务完成表现与让人理解 Harness 的进化过程，是相互关联的核心目标。用户能够看懂插件的作用、设计动机、组合变化和选择依据，并将选定执行版本便捷地导出为精简、可脱离 Meta 和原开发仓库运行的独立 Harness 项目。

项目遵循 DeepSeek Harness 的 “Everything is Plug-in” 原则，从最小可运行的执行 Harness 基线出发，由 Meta 自主开发职责清楚的执行插件。具体的插件版本及其配置组成不同候选，在可比较的任务与运行条件下评估通过率、重复执行的稳定性与资源消耗。插件化既支持对具体能力进行有针对性的优化，也为理解能力组合与任务表现之间的关系提供结构基础。

可读性与可解释性贯穿插件划分、版本组织、实验比较和研究记录。具体要求落实于第 3.1 节的插件职责与动机、第 3.2 节的组合测试、第 4.4 节的插件与版本及实验关联，以及第 4.6 节的进化方向阅读。

系统围绕四类核心能力构建：**插件开发、组合测试、读取证据、生成报告**。模型可以自由组合和反复使用这些能力，自主决定研究什么问题、如何修改、测试哪些候选、是否继续验证或回退。

本文不规定模型的改进算法、分析顺序、搜索策略或每轮修改数量，不预设必须开发哪些插件，也不要求一般研究过程配置独立的失败分析器、提案生成器或固定的多 Agent 流水线。第二类主动停止需要独立审查，见第 7.4.1 节。提交候选时需要简短说明修改目的与依据，但不以完成固定分析表格或证明原因假设为前提。

必须保留以下原则：

- **固定 Solver，开放 Harness 设计。** 用户分别选择执行模型与 Meta 模型，研究执行插件及装配方式带来的效果。
- **以插件表达能力，以组合形成版本。** 插件职责、依赖和协作关系清楚，在合法组合中可以调整、替换、移除和比较；不预设固定插件数量或粒度。
- **可自由探索，按证据认定效果。** 允许失败、退化和证据不足的尝试；“值得测试”与“已经有效”分别记录。组合表现改善不自动证明各插件都有贡献，插件作用与相互作用须结合轨迹、对照、重复测试和必要的消融判断。
- **边界由固定基础设施保证。** 模型可以改变执行策略，不能改变评分权威、信息权限、真实预算和原始记录。
- **以可复用能力和泛化为目标。** 改进应能用于目标任务范围内的新任务或实例；结论不得超出已有证据。
- **过程可读，结果可追溯。** 简明报告解释变化与决定，详细记录支持核查；失败分支同样保留。
- **进化方向对人类可读、可解释。** 人能理解正在解决什么问题、每个插件的作用与设计动机、组合如何演变、证据如何改变判断，以及为什么选择或继续验证某个版本。先提供独立可读的高层描述，再按需进入解释与依据；已有细节不等于已经可读，解释不代替效果验证。
- **按插件保存版本，按需装配交付。** DeepSeek Harness 记录准确版本引用；插件内容与组合清单持久保存并复用，安装缓存和完整项目不随每个候选重复保存。
- **继承通用能力，完整保存、按需读取。** Meta 使用原生 Agent 能力开展研究；长输出和完整证据以可访问文件提供，摘要、分页和压缩不能代替或删除完整来源。
- **Meta 本身也可实验。** Meta 组合应可替换、冻结、复用和观察，为独立活动之间的公平对照与合法消融保留基础；保留插件的理由和适用范围可复查。

后续研究方向还包括 Meta Harness 本身：通过修改、更换、添加和移除 Meta 插件，比较它们对设计执行 Harness 的帮助，并通过重复和消融实验保留有作用、成本合理的能力。Meta 的设计能力和 Solver 的执行能力分别评价，以实际成果、可靠性和资源消耗为依据，不以插件数量或活动数量代替进步。当前可比较性基础与后续范围见第 2.5 节。

## 2. 模型分工与运行关系

### 2.1 模型职责

| 角色 | 谁来选择 | 职责与约束 |
|---|---|---|
| 执行模型（Solver） | 用户选择一个固定模型 | 在执行 Harness 中读取当前任务、调用工具、自主设计实验与科学求解、生成并提交结果；一次进化活动中固定模型及调用设置 |
| 开发模型（Meta 模型） | 用户独立选择，通常选用能力更强的模型 | 使用 Meta-Harness 提供的能力开发插件、组织测试、读取允许的反馈、分析结果并撰写报告；自主决定如何改进 Harness |
| 参考模型（可选插件） | 用户从 DeepSeek Harness 原生配置选择并批准一个或多个 | 在独立参考实验中运行当前执行 Harness；同时启用 Harness 插件时也可运行已选参考 Harness，提供结果与轨迹；不接管主线 Solver，不预设比 Meta 或 Solver 更强 |

用户可在工作台全局「供应商与模型」管理连接、API Key 和模型目录；新建活动提供返回原草稿的管理入口。配置保存无需重启即可用于新活动，已有活动仍使用创建时冻结的路由与模型能力。密钥不回显，不随配置、活动或导出分发；供应商设置和测试仅对用户开放。测试调用由用户主动发起，单独展示实际响应、工具往返及已知/未知用量，不以密钥存在或地址可达代替模型验证。

主线 Solver 与 Meta 分别配置、记录和计量。系统不绑定特定模型，也不要求证明 Meta 模型一定比 Solver 更强；接入能力以实际支持为准。更换主线 Solver 或其调用设置后，应开启新的进化活动，重新验证效果。Meta 模型或其设置发生变化时，记录生效时间及对应候选，保留开发来源。第 3.5 节的参考模型使用独立执行配置和结果分组，不改变本活动固定 Solver；参考模型配置以 DeepSeek Harness 原生配置为权威，不另建供应商目录。

主线执行阶段的模型推理仅使用指定 Solver 及约定调用设置。插件增加的模型调用、反思或重试均计入执行预算。Meta 模型不参与正在进行的 Trial，不接管求解，不通过辅助模型服务或提前生成测试题专属解法进入执行过程。参考实验使用全新任务和执行会话，不能向在途主线 Trial 提供实时辅助。

### 2.2 Meta-Harness 与执行 Harness

**Meta-Harness 是通用 DeepSeek Harness Agent 与 Meta 业务插件的组合**，在原生文件、终端、任务、会话和委派能力上提供四类研究能力，对外可作为一个 Meta 插件包安装。内部通过原生服务、工具、行为扩展和 Agent Preset 组合；停止审查使用独立身份、只读来源及隔离执行环境。无需为每个业务步骤拆出插件或另建插件管理器。权限检查、运行调度和结果记录由固定基础设施执行。组合职责见[插件组合设计](../design/meta-harness-composition.md)，能力、证据和恢复的完整目标见[专项设计](../design/meta-agent-and-evidence.md)。

**工作台优先作为 DeepSeek Harness 的 UI 插件**，向用户提供活动操作、版本比较、报告阅读和导出入口。Meta 工具插件与 UI 插件可以作为同一套件安装，但职责、身份和权限分别管理。

**后台运行控制独立于界面和模型会话。** UI 和 Meta 访问同一份持久状态及受控操作接口。后台可通过固定宿主插件接入，但调度、预算、证据归档和实验监督不能依赖浏览器页面、UI 插件或 Meta 会话存活。关闭页面或卸载 UI 不自动停止活动；主动停止后台时必须按已配置策略处置任务并保存状态，不得让在途工作失去监督。

**执行 Harness（Execution Harness）** 由准确版本的 DeepSeek Harness、选定的执行插件及其组合配置构成，必要外部依赖明确声明。平台负责实验监督与评测接入，不将整套平台代码默认纳入候选。开发会话与 Solver 会话隔离：每次测试使用干净的 Solver 会话与按任务要求重置的环境，不加载 Meta 插件，不带入开发对话、历史评分或此前任务状态。

Quantum-Harbor 提供实验环境和官方科学评分。Meta 使用允许的反馈研究改进，系统复用官方评估与归档能力。

### 2.3 最小概念

| 概念 | 含义 |
|---|---|
| Campaign／进化活动 | 固定 Solver、目标任务范围、基础设施、资源上限、比较与保留规则的一次开发活动 |
| 插件版本 | 独立保存的执行能力实现及必要资产，附名称、版本、用途、配置 schema、依赖和内容摘要，供多个候选引用 |
| Candidate／候选版本 | 不可变的组合清单，记录 DeepSeek 准确版本引用、精确插件版本、完整配方（Recipe）、有效配置与依赖锁定信息；不要求保存完整运行项目 |
| Trial／单次测试 | 一个候选在一个任务或任务实例上的一次独立执行及官方评估 |
| 测试批次／一轮测试 | 一个冻结候选及确定的任务、重复次数组成的测试批次；系统受理一次计一轮，对照关联其他候选的批次，计数规则见第 7.2 节 |
| 保留版本 | 按既定规则选中的候选，可以是 H0 或较早版本；与最新候选、待验证候选分开记录 |
| Meta 组合版本 | 冻结的 Meta 插件、配置、预设及依赖资产；属于开发来源，与执行 Candidate 分开记录 |

“轮”用于组织测试和报告，不约束模型的工作顺序。模型可以同时考察多个分支、为同一候选追加测试，或在证据不足时暂缓修改。

### 2.4 Meta 系统职责与动态活动目标

Meta 的系统提示词保留项目目的、Solver 与执行 Harness 的分工、插件设计原则、SDK 资料入口、研究自主性、证据判断、持续推进和报告交付。活动目标与固定 Solver 配置使用占位符，创建时填入用户配置；数值正确率、重复次数和达成标准不写死在模板。工具参数、修订与幂等协议、预算准入、计分兼容及恢复机制由工具描述、运行状态与资料提供，不重复追加到职责正文。

默认目标：持续改进执行 Harness，使固定 Solver 更有效、稳定地完成所选任务，并以可复核的执行证据说明改进效果。用户可采用或修改默认目标；缺失或空白时使用独立默认配置，不自行填入量化阈值。

模板正文见 [运行时系统提示词](../../src/control/prompts/meta-system.md)，UI 与后台默认值共用 `schemas/meta-defaults.json`。新活动冻结 `meta-system-v9` 和 `goal-or-budget-v1`，记录实际渲染文本及摘要；启动和恢复使用同一冻结版本。只有目标得到证据支持或额度达到上限时结束探索，具体控制规则见第 7.4.1 节。旧活动的目标、提示词、工具契约与停止策略均不追溯替换。

启动消息提供必要状态、能力和容器内资料导航；完整 SDK、报告字段及历史明细按需查询。普通回合结束后按状态续接，等待实验时使用完成通知。修改提示词不自动启动真实实验。

### 2.5 Meta Harness 作为研究对象

首期插件组合重构须为后续研究保留基础：每项可替换能力明确接口、依赖、关闭或替换后的行为；组合可冻结并保留实际加载记录；插件的触发、未触发、降级与失败可关联到对应活动。Meta 插件不得依赖未声明的共享状态，使不同组合之间无法独立比较。

未来可用完整 Campaign 比较不同 Meta 组合在共同条件下设计执行 Harness 的能力，评价最终保留的执行候选和设计成本。当前为此保留组合差异、活动来源和真实结果关联；不实现对照计划、重复调度或比较功能，也不要求每个组合采取相同的思考或实验步骤。

Meta 组合的保留与回退是独立决定，不能与活动内执行候选的保留混为一谈。研究新 Meta 版本使用新的冻结组合和独立活动；正在被评估的活动不自行修改自己的组合或规则。停止契约按活动创建时的版本执行，基础要求见第 6.3 节，范围见[插件组合设计](../design/meta-harness-composition.md#9-本次范围与后续边界)。

### 2.6 通用 Agent 能力与持久工作区

主 Meta 必须保留固定版本通用 Agent 配置中的文件读取、搜索、编辑、终端、长任务、资料/技能读取、上下文压缩、会话查询及普通子代理能力。具体原生配置以锁定版本验证为准；无界面运行不能作为关闭基本工具的理由。与活动权限不相容或依赖外部服务的能力明确记录限制及来源，不默默退化为最小工具集合。

插件草稿、分析脚本、检查结果与会话状态保存在持久工作区；终端支持真实开发和数据分析，包含明确版本的 Node/Python 及必要依赖。开发目录可写，证据和冻结版本只读；原生工具、脚本和子代理都能访问同一授权材料。权限由固定宿主和隔离环境保证，不依赖提示词或隐藏工具。

模型自行决定是否委派及如何安排研究，不强制多 Agent 流水线。普通研究优先复用原生子会话、消息和恢复能力，与主 Meta 共享活动内授权文件；独立上下文不要求独立容器。cwd 遵循原生语义，研究不附加隐藏的五分钟总时限。普通研究子代理与停止审查者职责分开，全部调用共用预算；主 Meta 不能伪造审查身份。Meta 插件主要提供领域动作，通用工作能力优先复用框架；验收以真实会话中的有效能力为准。

## 3. 四类核心能力

### 3.1 插件开发

Meta 必须能够阅读开发文档与已有插件，直接编写新插件，修改或替换实现，调整配置，并从组合中启用、移除插件。第一版就支持实际代码生成，不局限于已有开关或提示词搜索。

插件需有清楚的职责边界，能够独立装配和在合法依赖关系下移除或替代。相关机制可以一起修改，不要求每次只改一个插件。上下文组织、工具辅助、运行状态等均可成为设计对象；brainstorm 中的能力清单只作参考。

每个插件版本至少说明：名称与版本、普通语言的用途、主要行为及触发条件、输入来源与可观察范围、配置和依赖，以及禁用或输入缺失时的行为。源码与依赖指纹由系统记录，设计目的与已观察效果分别保存；未知信息明确标注，推断不能自动成为硬性限制。

开发或采用某个插件的活动内动机另按第 4.6 节记录：关联要解决的问题、允许的问题来源、预期变化与验证问题。通用用途与这次开发理由分别保存，不将研究轨迹或历史经验自动带入 Solver。

系统必须提供装配与边界检查。依赖缺失、配置无效或权限越界的候选记录为检查失败，修正前不启动正式效果测试。新增工具必须声明能力与权限，并通过检查，不能为此取消原有工具边界核验。

#### 3.1.1 与执行版本匹配的开发资料和查询

系统必须向 Meta 提供与目标执行 Harness 相匹配的插件开发资料及只读查询能力，帮助它正确实现自己的设计。资料说明框架事实、接口语义和项目边界，不规定改进顺序、搜索策略或必须使用的插件。

| 资料层次 | 必须覆盖的内容 | 提供方式 |
|---|---|---|
| 简短开发说明 | 执行 SDK 版本、目标 profile、工作目录、可修改范围、权限边界与资料入口 | 开发会话启动或恢复时提供必要摘要 |
| 按需参考与查询 | Cordis 生命周期、服务与事件、配置、工具注册、上下文扩展、依赖与装配规则，以及目标环境实际可用的接口 | 可搜索的只读文档、类型声明、必要源码与 API 查询，不要求一次性塞入全部资料 |
| 可运行技术样例 | 最小插件、工具注册、配置读取、状态记录、资源清理和合法移除依赖 | 与目标版本一起通过兼容性检查的少量样例，不包含测试题答案或预设科学求解流程 |

资料和查询结果必须标明来源、适用版本与目标执行环境，记录资料版本及内容指纹。不能将 Meta 开发宿主或 UI 宿主拥有的全部服务视为 Solver 环境也具备的能力。接口缺失、资料不匹配或能力尚未验证时，应明确返回状态；不得静默使用最新版本或让模型凭空假定接口存在。

查询只公开开发所需的接口声明、允许的配置 schema 和能力信息，不暴露凭据、私有路径、隐藏任务、受限评分或后台控制内部配置。查询不能调用业务方法、修改运行 profile、安装/启停插件或绕过候选冻结；生成代码的执行仍经过受控检查。执行插件的开发资料和查询不依赖浏览器在线，资料本身不作为 Solver 的任务输入。

#### 3.1.2 统一资料查询

Meta 必须能列出、搜索和分段读取当前活动允许的材料：活动约定与实时状态、所选任务原文和公开环境说明、版本匹配的 SDK、冻结插件源码及配置、执行版本与差异、实验记录、允许证据、历史报告分析、平台工具与报告契约。材料提供稳定引用及容器内可访问路径，支持原生文件工具和脚本处理；旧工作区接口作为兼容入口保留。

查询结果包含稳定引用、来源、适用版本或内容摘要；动态状态标明读取时间。支持类别、任务、候选和批次过滤以及分页，搜索覆盖完整允许文本而非仅开头片段。区分后台事实、执行证据与模型分析；旧分析不自动升级为事实，原始证据 ID 仍用于报告引用。

只索引明确允许的来源，不开放任意宿主路径或整个任务仓库。新活动保存公开任务原文快照；历史活动读取当时归档的原文，缺失时明确不可用，不用当前任务文件冒充原输入。冻结源码按候选引用的插件内容摘要校验，旧格式继续校验原 Bundle；SDK 按活动/基线绑定的资料包查询，版本不匹配不静默回退。查询不依赖浏览器、不执行被查询代码、不改写历史记录。

### 3.2 组合测试

Meta 必须能够选择插件版本与配置，组成候选执行 Harness，选择允许的任务、各任务重复次数，并提交测试、查询状态和收集结果。

任务数量与重复次数是两个独立设置，例如一个任务跑一次、一个任务跑五次、五个任务各跑一次。具体如何分配探索次数由 Meta 在活动规则与预算内决定；系统记录计划次数、实际启动和完成次数及所有尝试。受理批次和启动 Trial 时均需执行第 7 节的额度检查，不得通过扩大单轮任务数、重复次数或并行数绕过运行上限。

每次测试前冻结候选，保存父版本或来源、简短修改说明及不可变组合清单；清单引用已保存的精确插件代码、资产、配置及锁定依赖。同一插件版本只保存一次，修改配置或增删插件不重复复制未变内容。正在运行的候选不得随开发区编辑而改变；实际加载内容与声明不一致时标记异常，不把分数归给声明中的组合。

测试支持 H0 对照、父版本对照、移除或替换插件的消融，以及不同组合和配置的比较。具体采用哪些由 Meta 决定，不要求每轮穷举。移除插件时必须保持其他条件可比，说明依赖处理；必要时恢复基线行为或使用无操作替代，不能把依赖断裂造成的连带失效当作单插件贡献。

“卸载插件”通常体现为新候选中移除该插件。历史插件版本、候选和测试结果仍然保留；不要求在进行中的 Trial 内热替换插件。

### 3.3 读取证据

Meta 必须能够读取允许范围内的官方评分与诊断、执行轨迹、工具返回、提交产物、插件运行记录和资源消耗，并定位到具体 Trial 和证据片段。成功、失败及未完成运行都属于可研究的证据。

证据接口必须满足：

- 保留官方原始结果；区分未评分、基础设施或模型接入故障、超时／预算终止、未提交、无效提交、科学未通过和科学通过，允许多个状态并存。
- 官方缺失评分保留 null，官方零分原样保留。新活动默认绑定 task-completion-v4：已经进入启动尝试且最终结束，只有可信官方通过计 1，其余计 0 并纳入任务成功率，包括模型、插件、容器、评分、收集、资源终止和原因未明的结果缺失。运行中或进程状态尚待核实不提前结算；尚未启动和无先行失败的明确人工撤销单列。官方结果优先，失败后再人工停止不能免除失败。结果与归因分开，界面优先显示失败及原因，官方未评分放详情。已有活动保留 v1/v2/v3 绑定，缺少字段按 v1 读取，不回写历史。具体边界见[任务完成规则 v4](../design/task-completion-v4.md)。Solver 停止、提交被接受和科学通过分别记录。
- 插件的配置、实际加载、触发、未触发、降级与失败有可核对记录；无法观察的行为标记未知，不能推定未发生。
- 提供完整证据的受控入口，支持摘要和按需读取。摘要保留来源，不改写权威结果，不要求取得模型的隐藏思维过程。
- 官方评分报告、完整可用轨迹、工具返回、实际提交、执行/桥接/评分日志和恢复事实均有可访问文件。未知诊断字段和事件类型不能仅因不在通用白名单中被删除；需要转换的视图保留原件入口及覆盖说明。
- 长工具返回和命令输出在展示裁剪前完整落盘，响应可以只含预览、来源路径、字节数和完整性状态；失败、超时和取消也保留已取得内容。达到存储或执行边界时明确说明不完整原因，不能静默丢失后声称完整。
- 区分原始归档、可访问视图和摘要。按第 5、6 节处理明确受限的信息，记录任务级策略及受影响范围；正常评分指标和失败诊断默认完整可读。摘要长度限制不能成为限制材料访问的依据。

### 3.4 生成报告

Meta 在读取一轮测试证据后，必须生成或更新该轮报告，解释测试内容、结果、判断与后续决定。进化结束时，必须交付一份简明的最终总报告。检查失败、运行中断或无可用评分的尝试也需有对应记录和状态说明。系统按第 7.4 节预留收尾资源；强制中断或模型不可用时，至少生成不依赖模型的状态摘要，并标明完整报告尚未完成。

版本、配置、分数、次数、成本和差异由系统记录生成；轨迹分析、解释和决策理由由 Meta 模型撰写。报告以真实记录为依据，不能依靠自由叙述补齐缺失信息。具体内容与阅读要求见下一节。

### 3.5 可选参考模型与参考 Harness 插件

新增两项独立可选能力，完整行为见[参考实验插件设计](../design/meta-reference-experiments.md)，实施见[开发计划](../plans/meta-reference-experiments.md)：

- **参考模型实验：** 用户从 DeepSeek Harness 原生 profile/provider 配置选择参考模型及调用设置；活动冻结来源和有效配置，Meta 按需选择已批准模型运行本活动的冻结执行 Harness。Meta 模型仅是可匹配时的快捷选项；原生配置后续变更不热改旧活动，不维护第二份参考模型目录。
- **参考 Harness 实验：** 默认使用活动固定 Solver 及约定调用设置，首期可选 Codex、Claude Code 和 DeepSeek Harness 标准模式，后者必须区别于本项目 H0 的极简配置。通过版本化适配接口扩展其他 Harness，不将某个品牌写死到 Meta 工具；不兼容的模型、环境或计量配置明确不可用，不静默换模型。
- **联合参考：** 两插件同时启用时，允许已选参考模型 × 已选参考 Harness；由共享后台同时校验两项能力，不新增第三个必需插件或相互装配依赖。每次运行只有一个准确模型绑定，不能借联合模式在运行内暗换模型。
- **UI 与选择权：** 提供两个独立开关、原生模型和 Harness 多选，以及“由 Meta 自主选择 / 我指定组合”。自主模式只允许已选集合内经核验的兼容配对；指定模式只允许用户指定的配对。矩阵显示支持、不支持、待核验与暂不可用及原因，不承诺任意模型互通。Meta 自主安排任务、时机和重复，不自动穷举；选择理由、准确配对与轨迹可追溯。
- 两插件各自拥有入口、契约、说明和生命周期，无相互硬依赖；无插件、仅任一插件、两者同时启用均是合法组合。移除后没有相应新执行权限、自动调用或残留依赖；停用任一能力取消依赖它的排队工作（含联合参考），另一插件的单维参考和主线继续可用。历史证据仍可读，已开始工作及冻结资产按设计分别处理。
- 参考运行使用独立任务实例和干净上下文，遵守同一任务权限、官方评分和活动预算。结果、消耗、轨迹及条件差异必须留存；只能形成研究启发，不能直接作为主线候选或混入其成绩。
- 不规定 Meta 必须何时运行或使用几个参照，不强制逐轮执行；提供研究目的与证据关联即可，不预设成功标准答案。参考模型/Harness 和研究材料不自动进入 Solver 独立导出。

本节为 v0.15 待实现需求，既有六个领域插件和旧活动不因文档更新获得新能力。

## 4. 每轮报告与最终总报告

### 4.1 每轮报告：这次测试发生了什么

每轮报告对应一个测试批次，关联候选、Trial、对照结果和证据。目的在于让用户无需阅读完整日志，就能理解本次尝试及其对后续开发的影响。

| 内容 | 必须回答的问题 |
|---|---|
| 简短结论 | 这一版目前表现如何？准备保留、修改、移除某插件、回退、继续验证还是停止？结论有多大把握？ |
| 本次变化与目的 | 相对哪个父版本或基线改了什么？为什么测试这一版？未修改、仅重复测试时说明验证目的 |
| 执行 Harness 的组成 | 使用哪些精确插件版本与配置？每个插件的用途是什么？完整代码、依赖与配方在哪里？ |
| 测试条件与结果 | 测试哪些任务、各跑几次，实际完成几次？Solver、环境和预算是什么？官方评分、失败情况、耗时和用量如何？ |
| 运行控制与消耗 | 受哪些轮次、时间、Trial 数、用量和并行上限约束？本批次实际消耗及活动累计消耗、已预留与剩余额度是多少？是否暂停、中止或部分完成，原因是什么？ |
| 轨迹分析 | 关键事件是什么？插件实际做了什么？哪些行为或结果与之前不同？如何解释，有哪些不确定性？ |
| 后续决定与依据 | 哪些证据支持当前决定？接下来做什么，或为什么暂不修改？后续实际行动关联到哪个版本或批次？ |

这些是报告的信息要求，不是模型必须依次执行的分析步骤，也不要求每次报告使用固定表格。

**轨迹分析重点回答：**

- **实际发生了什么。** 提炼影响结果的关键动作、异常与转折，并引用证据；不逐条复述全部工具调用。
- **相对之前有什么变化。** 分别描述行为、评分和成本；标明比较对象、可比条件及无法控制的差异。没有有效对照时明确说明。
- **插件实际起了什么作用。** 说明是否触发、提供或修改了什么、预期行为是否出现；用途说明不能充当效果证据。
- **如何解释结果。** 分清观察事实与原因推测，指出相关的其他解释和未知项。未达标指标本身不等于失败原因；事件先后关系不自动证明因果。
- **证据支持到什么程度。** 允许结论为证据不足、插件未触发、只改善提交或未发现收益。必要时说明什么额外证据有助于判断，具体是否开展验证由 Meta 决定。

多次运行先概括共同现象，再呈现波动和重要例外，保留逐次结果入口。成功率注明分子、分母、未评分和故障次数；重试不能覆盖原尝试，不得通过筛除失败制造提升。耗时区分整个任务与模型／工具执行阶段，未知用量明确标注。

### 4.2 最终总报告：整个进化过程发生了什么

最终报告应使用户在几分钟内读懂起点、关键变化、结果与局限。按关键转折重新组织内容，不机械拼接每轮报告。主报告至少包含：

| 内容 | 必须呈现的信息 |
|---|---|
| 起点与最终选择 | 固定 Solver、Meta 开发模型及变更记录、目标任务范围、初始 Harness、最终选定版本及选择理由；最终版本可以早于最新尝试 |
| 效果与代价 | 基线与最终版本在可比条件下的逐任务结果、样本量、稳定性证据、退化及执行成本；另列整个进化活动的开发和测试消耗 |
| 上限与实际消耗 | 初始及用户调整后的上限、受理轮数、计划／启动／完成／中止的 Trial 数、实际总时长与暂停时间、Meta 与 Solver 的用量及剩余额度；计量缺失与超限情况明确标注 |
| 关键演化过程 | 主要分支与转折、有效或无效的尝试、哪些证据改变了判断、为什么保留或放弃某方案，并链接每轮报告 |
| 最终插件组成 | 各插件的用途、精确版本与配置、保留理由和支持证据；区分已验证作用与设计预期，并概述重要的移除或替换决定 |
| 泛化与未解问题 | 哪些任务参与过开发或选择、哪些独立用于最终测试，现有结论适用范围、未解决失败和证据不足之处 |
| 停止与交付 | 主停止原因及触发时间、同时触发的其他限制、采用的截止策略、进行中任务的处置、收尾实际消耗与未完成事项；选定配方、独立执行项目导出入口与内容指纹、安装启动方式、导出包独立运行验收结果及证据入口 |

演化过程可采用简表：**版本／分支、主要修改、测试结果、当时判断、后续决定**。有分支时保留真实继承关系，不把时间顺序画成单一路径。主报告突出关键尝试，所有失败分支与未完成记录仍可在详情中找到。

没有可靠改进时，明确报告负结果和保留 H0 的理由；没有独立评估时，明确标注泛化尚未验证。最终报告不以“必须证明成功”为目标。

报告必须区分正常提前结束、用户停止、轮次或 Trial 额度用尽、时间到期、用量预算不足和运行故障。展示配置的截止时刻与实际结束时刻；采用允许当前任务结束的策略时，明确其额外耗时。尚在运行、已请求终止与已确认终止分别显示，不把待核实的外部运行写成已清理。

### 4.3 阅读层次与真实性

- 默认提供简明中文摘要，插件附普通语言用途说明。精确配置、代码差异、逐次结果和完整轨迹通过详情或链接查看。
- 高层概述与详细解释分别表达完整含义，不以截取长文本开头代替概述。关键局限与结论同层可见；概览和版本比较默认展示逐任务表现及实验进度，逐次明细再按需展开。
- 报告必须可持久保存，在 Meta 卸载后继续阅读。建议采用结构化记录与本地可浏览报告，可附 Markdown 摘要；不强制前端技术或在线服务。
- 每轮保存当时的判断、时间和证据引用。新证据可以修订判断，但需保留修订历史，不事后重写当时的决策依据。
- 运行事实、模型解释与选择决定可以区分。缺失证据显示缺失，受限证据显示访问限制；报告及其链接遵守相同的信息边界。
- 工作台按第 7.8 节优先作为 DeepSeek Harness UI 插件；当前分层阅读参考及可调整范围见 [Studio 设计第 13 节](../design/meta-workbench-studio.md#13-演化过程的分层阅读演示2026-10-22)。参考页面的信息层次用于实现目标，布局、样式与具体操作可按项目约束调整。

### 4.4 三张关联表：插件、执行版本、实验轮次

报告与工作台共用三张表，保持插件、版本与实验关系直接可达。活动总览与最终报告先展示概述、逐任务表现和关键转折，完整三表可折叠或链接查看；每轮报告先讲本轮结论与变化，不将完整三表重复放在开头。插件功能不藏在源码摘要或原始配置中。

| 表 | 一行代表什么 | 默认信息与关联 |
|---|---|---|
| 插件表 | 一个精确插件版本，以名称、版本号、内容摘要区分 | 中文名称、精确版本、实现方式、普通语言功能说明；展开查看说明来源、源码身份、接口声明。一个插件可以有多项功能 |
| 执行版本表 | 一个冻结的执行 Harness 组合 | H0/H1 等活动内稳定短名称、来源版本、按加载顺序排列的插件精确版本、保留/最终状态；插件链接到插件表，配置与完整身份可展开 |
| 实验轮次表 | 一个已受理测试批次 | 轮次、执行版本、相比上一受理轮次的插件变化、任务及重复次数、逐次评分与未评分项、报告/证据入口；版本和变化中的插件均可定位到对应表 |

轮次不等于新版本。同一版本可多轮复测；首轮注明没有上一轮比较对象。并发时按受理轮次比较，不按完成顺序；回退和分支保留真实来源，不能把“父版本”当成“上一轮版本”。同名同版本号但源码摘要不同的插件必须分行并提示内容变化，不静默合并。

变化由系统从冻结记录计算，覆盖插件新增、移除、版本/内容更新、配置修改和共有插件加载顺序变化。启停若通过配置实现，展示配置键及前后值；不臆断任意配置键的执行语义。插件无变化但其他执行内容变化时明确区分；缺少比较记录时显示无法比较，不能写成“无变化”。任务、重复次数与评分另列，不能当作插件变化。

插件表说明设计能力，轨迹分析说明实际作用与效果。实现方式必须能区分提示词建议、可调用工具、自动检查、拦截/控制等，允许组合；不因某接口声明而认定源码已实现强制检查。说明可来自冻结清单或绑定精确内容摘要的补充记录，必须保留来源；补充说明不得冒充原始 Meta 判断。

每轮报告的三表范围截至本轮，包含理解差异所需的前轮与父版本，不带入后续新候选。最终总报告展示全活动三表，并突出最终版本及关键解释；每轮分析、失败记录、精确配置和原始证据仍可追溯。已有活动可在不调用模型、不重跑实验的情况下追加展示修订，保留原报告、原分析及事实快照。三表是记录和阅读要求，不规定 Meta 的改进方法或分析步骤。

### 4.5 面向阅读的名称、过程与复测汇总

- 版本使用活动内稳定短编号加功能名称，例如 `H0 · 原始基线`、`H1 · 科学计算审计版`。Meta 可提议名称，用户可修改展示名；不改变冻结内容。报告正文、版本决定、导航与下载文件名不直接暴露 UUID 或长哈希，精确映射保留在 JSON 与高级核验信息中。
- 每轮默认提供简短结论、本轮变化、任务表现、后续决定和关键局限；过程节点、已解决/未解决问题、插件作用与消耗明细按需展开。最终报告用同一阅读层解释起点、主要改动、复测波动、最终选择与局限，不能只拼接单轮分析。
- 插件作用分别写预期功能、轨迹实际观察、对照情况、判断及证据。提示词加载不等于模型遵守，遵守不等于产生科学收益；没有消融或可比对照时明确写证据不足，不为完整表格虚构结论，也不强制额外实验。
- 轮次表默认合并连续、完全相同执行版本且任务/执行条件可比的复测。展开保留每轮及每次评分、未评分、故障、报告与证据；不跨版本切换、不跨不同条件合并，不改计数和账本。
- 插件提供冻结版本的只读代码浏览、打开本机文件夹及复制路径。不能用活动草稿替代当时使用的源码；高级来源与清单信息折叠。只允许用户身份打开受控目录，Meta 不获得宿主文件管理权限。
- 历史阅读整理追加修订，保留原始分析/事实/文件。非原 Meta 新分析的阅读整理明确标注来源；缺失信息不补造。名称与格式整理不需要重跑实验。

### 4.6 进化方向的可读性与可解释性

本节落实[项目设计哲学](../design/design-philosophy.md)中理解进化过程的核心目标，规定进化阅读的产品要求。用户应能持续理解插件设计动机、组合演变与研究方向，不只在最终报告中看结果。具体记录与接口见[进化可读性设计](../design/evolution-readability.md)，界面见 [Studio 修改方案](../design/meta-workbench-studio.md#14-分层阅读的正式页面修改方案)。

| 阅读对象 | 必须能回答的问题 |
|---|---|
| 当前研究与关键转折 | 当前在解决什么问题，哪些观察促成方向变化，哪些尝试无效、被放弃或仍待验证？ |
| 插件的开发与采用 | 为什么值得写或采用它；问题来自哪些项目/活动、任务和轨迹；预期改变什么，实际验证到了哪一步？ |
| 版本选择 | 为什么选、维持或回退这一版；明确考虑过哪些主要备选，接受什么代价，有什么局限，何时重新考虑？ |
| 版本与任务表现 | 每个版本在各任务的成功数、纳入分母与成功率是多少；运行中、排队和其他状态各有哪些实验？ |
| 判断与依据 | 哪次实验的哪个片段支持这个判断；原文、报告和冻结实现在哪里；哪些事情仍不能由此证明？ |

概述、解释、原始依据逐层展开，默认层无需阅读源码、完整日志或长标识即可独立理解。数值事实由后台提供，Meta 显式提供动机、假设和取舍；观察、解释、计划、已执行动作和效果结论分别表达。既有文字太长时应提供有来源的独立概述，不能仅做视觉截断。页面读取不隐式发起模型调用。

研究记录与候选、插件精确版本、批次、Trial、报告修订和选择决定建立关联。代码父子关系与证据启发关系分别记录；同一插件在不同活动中的采用理由可不同。未形成候选、装配失败、负结果、回退和中止仍有对应记录，不要求每次研究必须形成成功插件，也不规定固定分析流程。

版本/任务矩阵默认比较基线、当前保留和最新候选（重复身份去重、缺失身份不补造），可调整比较范围。条件不同或缺失要就近说明，不展示无依据的提升或排名。成功率沿用活动绑定规则，运行和排队不混入纳入分母；没有结果不写成 0%。逐次明细保留轮次、状态、耗时、结果原因及报告/证据入口。实际阶段缺少上报时显示已知状态，不能从运行时长或无评分推断“正在测量/评分”。

若问题来自先前项目或活动，必须保留准确来源及允许访问的证据。跨活动材料通过显式纳入目标活动范围的记录提供，不允许 Meta 直接查询任意其他活动；未经纳入的原始 ID 继续拒绝。历史启发与当前实验事实区分，历史成绩不混入当前成功率，反馈暴露记录继续有效。

每个判断保留作者、时间、所依据的事实范围和修订；新结果可以改变认识，但不覆盖旧理由。旧记录未包含动机、备选或片段时明确显示未记录；后续整理作为有来源的新修订，不能倒写成当时已知。关键解释缺失或模型不可用时仍能查看已确认事实，不能用演示文案补齐。

## 5. 必要的权限与信息边界

### 5.1 修改与运行范围

Meta 自主修改的范围限定为指定的执行插件及其装配配置。模型接入、工具传输、环境权限、官方评分器、任务隐藏材料、真实预算上限、证据归档和版本选择的权限、核验及记录契约由固定基础设施维护；新活动的版本取舍由 Meta 自主决定。需要改变这些前提时，应作为独立基础设施变更记录并重新建立比较条件。

自动生成插件的检查与运行必须在受控进程／容器和访问权限内进行。Cordis 插件作用域不等于安全沙箱，不能仅靠提示或插件自检限制权限。执行插件不能读取模型凭据、宿主机私有资料、隐藏 verifier 文件或 Meta 开发历史；外部副作用受环境权限约束。

基础审计、权威原始证据及真实资源限制不可被插件或消融关闭。插件须说明实际观察和干预的路径；Solver 通过容器内 Python 访问 MCP 等路径时，不能假设某个工具 hook 已覆盖全部行为。

### 5.2 可复用执行能力

执行 Harness 可以根据当前任务公开信息、工具能力和实际运行状态适配行为。任务信息缺失时，相关能力应合理降级，未知或推断不得擅自转化为硬性限制。保留任务原文、工具原始结果及可回查来源。

不得将历史任务答案、隐藏参数、任务专属科学求解流程或预计算解法固化为执行资产，也不得按任务 ID、固定文本指纹等识别已知题目并切换专属求解脚本。实验方案、科学算法和具体结果由 Solver 在当前任务中自主形成。

Solver 不接收开发对话、历史评分、进化排名或保留测试反馈。Meta 默认可读取开发任务的完整评分报告和诊断；任务契约明确禁止用于优化的隐藏答案或真值按任务级规则隔离，保存原件及策略版本，并说明哪些范围未开放。不得用通用字段白名单默默删除正常诊断或把派生视图冒充原件。代码和提示看起来通用不能单独证明泛化，仍需独立评估。

## 6. 比较、保留与泛化要求

### 6.1 从第一版确定评估边界

每次 Campaign 开始前记录两个模型的配置、基线、目标任务范围、基础设施与环境版本、资源上限、主要指标、比较与保留规则、验收所需重复条件和停止条件。探索批次的任务与次数可由 Meta 自主安排，证据核验与记录契约不得为了让某个候选获胜而追溯修改；新活动不以固定成绩门槛代替 Meta 的版本取舍。

任务或实例的用途和反馈可见范围必须明确：

| 用途 | 反馈与使用规则 |
|---|---|
| 开发任务 | Meta 可读取允许的评分、轨迹和产物，用于开发与探索 |
| 验证任务 | 用于选择候选；结果参与选择或回流开发后，属于优化过程，不能再当作最终独立证据 |
| 最终保留测试 | 在最终候选选定并冻结后使用，结果不再用于本轮搜索、配置调整或版本选择；允许的结果可用于最终报告 |

只隐藏详细轨迹、反复返回总分也会影响搜索，不能因此继续声称测试集独立。最终测试后若继续利用反馈改进，必须记录该事实，并使用新的独立数据支撑后续泛化结论。最终报告的生成不重新开启搜索。

当前已分析过的五个公开任务均可用于开发和回归，不再视作未见测试集。区分同一任务重复运行、新参数或独立实例、新任务类型的证据范围。缺少独立任务时仍可开发和交付候选，但须标注“泛化尚未验证”；任务划分和反馈隔离从第一版落实。

### 6.2 效果证据与版本保留

比较候选时固定 Solver 及调用设置、任务版本、环境和可比较的执行／工具预算，列明无法控制的差异。随机种子可控时记录，不可控时通过独立重复观察波动，不承诺逐字重放。配置不同的历史运行可以提供设计线索，不能直接证明某项插件有效。

默认以官方科学通过表现为主要效果依据，同时报告有效提交、故障、逐任务指标、成本和退化；不同任务的原始指标不任意相加。开发成本与执行成本分别记录，额外调用、重复尝试和失败运行均计入消耗。

Meta 自主决定选择、维持、回退或继续验证哪个冻结版本，平台负责核验候选身份与合法证据、标注比较限制、保存完整决策。新活动不自动选择首个有评分版本，也不按固定均分/完成率门槛否决 Meta 的选择；可以有依据地选择尚无评分的 H0。每次选择提交理由、证据引用、科学表现/执行可靠性/时间用量的取舍、局限和重新考虑的条件。选定版本与证据支持程度分别展示；选择不是稳定性、因果收益或泛化认证，最新版本或一次高分不自动获选。

平台依据所选版本与此前保留版本的全部尝试，保存逐任务有效官方评分、完成率、未评分原因、在途与取消情况、环境差异和成本。缺少有效结果、样本不足、在途试验、指标退步或环境身份缺失/变化须明确标注，不阻止新活动的版本选择。Meta 可基于这些限制作取舍，不能隐藏反例或改写官方缺分；版本比较统一使用后台派生任务成功率，按规则计 0 的失败必须进入分母。证据引用必须属于本活动并通过内容摘要核验；候选须通过装配检查且组合及引用内容完整，旧格式继续核验原 Bundle。每次决定追加独立、带时间的记录，绑定候选内容身份、此前版本/决定、模型判断和平台事实快照；后续结果不得改写旧快照。选择契约在创建时绑定版本，旧 v1/v2 活动、旧报告和已结束选择不追溯改写。

消融说明插件在当前组合中的条件贡献，不直接证明普遍价值。未触发、无法独立拆分、缺少重复或存在依赖影响时说明限制；轨迹回放可以检查触发和注入行为，不能代替实际效果测试。

### 6.3 Meta 组合的可比较性基础

本次只定义未来比较所需的 Meta Harness 基础，不实现比较管理、批量重复、统计分析、专用界面或真实对照实验。插件组合重构应满足以下要求：

- 插件接口、依赖、配置和关闭后的行为明确；可以检查替换或移除是否合法，无法独立移除时说明依赖组或基础实现。
- Meta 组合可冻结并恢复，保留精确资产、父版本、差异和实际加载回执；活动关联其真实组合，不仅记录可变名称或路径。
- 活动记录模型、起始执行版本、任务与环境、目标、材料、预算和停止约定，并关联最终保留的执行候选，为以后识别可比较条件提供依据。
- 插件加载、触发、未触发、降级和失败可观察；能可靠归属的成本与活动关联，未知信息不猜测，共享调用不重复计量。
- 不同活动的会话、工作区和插件状态相互隔离；共享缓存、历史和长期记忆明确来源与初始内容，不能无记录地继承其他活动成果。

未来比较以完整活动及其最终执行成果为主要对象，同时考虑设计可靠性和资源消耗。重复与消融用于研究插件在具体条件下的贡献，不以插件数或一次结果证明普遍价值。失败、无改进、外部故障和材料反馈来源需要保留，具体研究计划、统计及评估方法在需要时另行设计。

预算、权限、原始评分和证据完整性属于共同约束。新活动仅支持目标达成或额度上限结束探索；旧审查策略的活动不能通过卸载插件绕过其门槛；研究新 Meta 组合使用新的冻结版本，不在正在被评估的活动中自行改写规则。设计调整和当前边界见[专题第 8、9 节](../design/meta-harness-composition.md#8-为后续比较保留的设计基础)。

### 6.4 参考实验的比较与来源

模型参考、Harness 参考和联合参考结果与主线候选分组统计，可按任务并排比较，明确模型、Harness、输入暴露、资源、能力差异与样本覆盖。官方结果和派生任务完成分沿用活动规则，参考分母不进入主线成功率、版本选择绩效或稳定性判定。参考运行可作为研究记录与版本取舍的解释依据，最终效果仍由固定 Solver 验证。

同时改变模型与 Harness 的参考结果不得单独归因；比较须展示同模型/异模型/待核验和准确对照对象。可按需组成四格对照，但缺少兼容配对时保留证据缺口，不自动补跑或替换模型。

首期供 Meta 学习的参考实验限于允许反馈的开发任务。参考证据引用准确运行、摘要与片段，保留失败和未知信息；轨迹启发、机制假设和已验证效果分开记录。停止审查与活动收尾必须核对参考在途工作和消耗。中途关闭插件不能清除 Meta 已读知识，不能将其当作干净的无插件对照。

## 7. 运行控制、持久记录与独立交付

### 7.1 持久记录与恢复

系统自动记录并关联 Campaign、插件版本、候选、测试批次、Trial、报告及保留决定。候选保留父版本／来源和差异；Trial 关联 Harbor Job／Trial ID、请求与可确认的实际配置、实际加载组合、原始结果、用量和证据索引。关键资产保留内容指纹，不要求建立独立的提案对象或固定分析 schema。

执行版本的持久保存单位是插件版本和组合清单。DeepSeek Harness 仅记录准确版本、获取来源及必要校验信息；未发布的本地插件必须保存代码和必要资产，不能只留下版本名称或草稿路径。组合固定 profile/patch、插件配置和影响行为的依赖；平台、任务与环境作为实验条件另行关联。

框架安装、依赖目录和临时装配目录作为可重建缓存，在兼容条件下共享，不能为每个候选重复安装相同依赖。缓存缺失可按原引用重建，指定版本不可获取或内容不符时明确失败，不改用最新版。实验记录、开发材料和证据不因缓存释放而丢失。旧 Bundle 继续按原协议恢复；迁移与清理须另有经过验证的流程，不能由本需求更新直接删除旧资产。设计见[插件版本管理与按需导出方案](../design/plugin-versioning-and-export.md)。

记录必须支持重启恢复与重复收集。持久保存已受理轮数、Trial 计数、已消耗和已预留额度、开始与截止时刻、暂停区间、运行状态及停止原因。中断后先核实外部运行状态，避免重复启动或重复计分；无法确认时标记待核实，保留相关资源预留和不确定项，不将未知消耗按零处理。

### 7.2 用户配置与轮次定义

用户设置有限的整体时间上限；最大轮次、最大 Trial 数、总 token 软阈值均可选择不限制。新活动绑定 `meta-resource-planning-v1`，区分用户上限、Meta 运行计划和平台执行条件。Meta 自主分配并发、批次时长和收尾预留，可以修改自己的计划，不能自行提高或关闭用户上限。每项配置记录决定者与来源，未指定的 token、轮次和次数上限保持空值。用户主动调整上限时保存原值、新值和时间，不清零既有消耗；改变 Solver 执行条件仍遵守第 2、6 节的比较要求。

| 配置 | 定义与用途 |
|---|---|
| 最大测试轮数 | Campaign 最多受理的测试批次；启用参考策略的新活动包含主线及参考批次，分类展示；不规定模型开发步骤，旧活动口径不变 |
| 整体时间上限 | 从 Campaign 启动至结束的墙钟时间，包含 Meta 开发、排队、环境准备、Solver 执行、评分、分析、报告与清理；默认按严格截止执行 |
| 单次实验时间上限 | 一次 Trial 从开始启动到评分、归档与清理结束的总时限；Solver、工具和官方 verifier 原有的分段时限另外记录、继续生效，不扩大任务的原有限制 |
| 最大 Trial 总数 | 活动内允许启动的实验尝试总数，防止一轮提交过多任务或重复运行 |
| 总用量预算 | Meta 开发、Solver 执行及报告等模型调用的合计 token 或可可靠计量的费用；分别展示分项消耗，可另设分项额度 |
| 最大并行数 | 同时运行的 Trial 上限；并行运行共享总预算与截止时间 |
| 收尾预留 | 在整体预算内为必要的结果收集、报告、资产导出与清理预留的时间和用量 |

启用参考策略的新活动中，参考批次和运行与主线共享上述轮次、Trial 总数、时间、token 和并发上限；每个参考批次占一轮，受理预留、启动计次，失败和重试同样计量。两插件可有总额度内的用户分项上限，不能获得额外免费预算。联合参考只占一份活动次数、轮次、用量和并发，同时受两项插件子额度约束；总览按三个互斥参考分组计量，插件参与视图有重叠不能相加。单批一个配对，换配对需另受理批次。原生标准 Harness 的压缩、子代理和重试全部纳入相应参考运行。H0 最低覆盖名额按原流程先预留；其已受理后，参考实验可在共同限额内并行，不强制等待基线完成。细节见[参考实验预算设计](../design/meta-reference-experiments.md#8-预算排队与生命周期)。

配置入口优先展示总时间（小时）、可选轮次、可选用量和最高并发；Trial 总数、单次时限上限、用户最低收尾预留及截止策略放入高级设置。新策略中未填写单次时限时，由 Meta 分配批次时长；未填写收尾预留时不扣固定比例，由 Meta 制定计划。建议值不自动升级为用户约束；用户明确填写的单次上限和最低预留继续生效。启动 Meta 后先制定计划，再受理 H0 基线。任务固有时限与冻结配方能力仍需明确展示。

已受理批次保存条件快照。计划默认只影响未来批次；排队导致时长不足时，需要 Meta 明确接受缩短条件。提高总体上限不会自动延长已启动进程，界面及 API 必须返回实际生效范围。默认启用有限的整体时间上限；用户另设绝对截止时刻时须带时区，实际截止取它与整体时限的较早者。没有新策略标记的历史活动继续采用原来的至多 1 小时单次自动时限、10% 且有封顶的自动预留，不热迁移。接口及验收见[资源规划计划](../plans/meta-resource-planning.md)。

**轮次和 Trial 按以下口径计数：**

- 一个候选的一次批次提交在通过检查、额度校验并被系统受理时计一轮。一个候选测试五个任务、每个重复两次，是 **1 轮、计划 10 次 Trial**。编辑插件、查看轨迹、生成报告不单独计轮，但仍消耗时间与用量。
- 批次受理后，候选、任务列表与重复次数固定。为同一候选追加测试、重试或测试另一候选，按新批次受理并计新一轮；不把新增尝试悄悄并入旧批次。
- 已受理的批次即使失败、中止或未全部启动，也占用这一轮；检查或额度校验被拒绝的提交不占测试轮次，但保存失败记录及已发生的开发消耗。重复查询、收集或重发同一受理请求不重复计轮。
- 每次实际开始启动 Trial 就消耗一次尝试名额，启动失败、科学失败、超时和中止均计入。批次受理时预留计划 Trial 名额；未启动部分取消后可释放预留，已启动名额不退回，计划数与实际数分别显示。
- 基线、对照、消融、复测、最终保留测试和独立运行验收均遵循相同的轮次与 Trial 计数。重试保留原尝试，不作为免费补跑；复用已有记录不新增测试计数，并标注其来源与可比性。

轮次和 Trial 总数是准入额度。最后一轮或最后一批名额获准后，不再接受超额批次，但已受理且预留额度内的工作仍可继续；它们仍受时间与用量上限约束。额度用满后停止新增探索，保留必要的分析与收尾，不能因轮数刚达到上限就立即取消最后一轮。

不限轮次/Trial/token 用真实空值表示；不使用极大数字代替，也不把空值当零。不限制某项不撤销其他已设置的约束；即使 token 不限，实际与未知用量仍计量。最高并发保持有限正整数。工程保护可限制单批提交体积（当前最多 100 次），不是活动总次数上限。

### 7.3 时间与预算执行

预算由固定基础设施执行，已启动任务的截止与超时约束在 Meta 进程退出后仍须生效。系统在受理批次、启动 Trial、发起 Meta 或 Solver 模型调用前检查已消耗、已预留、收尾预留和剩余可用额度。并发工作必须共享同一份预留与扣减记录，不能分别把同一余额用满；剩余额度不足时拒绝启动并记录原因，不静默缩小批次或降低 Solver 配置。

默认的严格截止将所有工作限制在整体时限内。新策略的计划收尾预留可暂缓新工作，不追溯缩短已受理任务，也不能作为 Meta 绕过停止审查的理由。单次 Trial 时限只终止对应 Trial，是否继续探索由剩余总额度和 Meta 决定；整体截止则停止整个活动的新开发与测试。因整体预算提前截断的 Trial 明确标记，不能当作按原定条件完成的对照。

用户可在启动前选择“到点停止新工作，允许当前任务结束”。此时该时刻是启动截止，不是严格的整体结束上限；只有已经启动的开发或实验工作可在各自时限和剩余用量内结束，排队但未启动的 Trial 取消，必要的报告与清理使用预留资源，并受有限的收尾等待时间约束。报告须展示可能超过的计划时长及实际延长时间，Meta 不得自行切换此策略。

时间与用量均包含失败尝试、额外调用、重试、分析和报告。费用不可可靠计量时不启用美元硬预算、不编造金额，改用可执行的限制。对于用量延迟回传或请求无法可靠限定最大消耗的接入，必须显示已确认用量与在途预留、采用保守准入并记录实际偏差；不能把软停止阈值宣称为精确硬上限。不支持可靠硬限制时，应在启动前明确不支持该配置。

临时被在途请求占用的额度需要等待结算后重新评估；等待不调用模型、不重复预留，也不算模型重试。Meta 计划预留阻止 Solver 时通知 Meta 调整。请求准入的等待、拒绝与实际模型调用分别记账；账本或凭证故障不能归为供应商错误。v4 中已经启动并结束的预算、账本和凭证失败计任务完成分 0，尚未启动的拒绝不进入分母；官方空值和具体原因保留。旧 v3 继续沿用预算截断、账本/凭证外部故障不进入分母的原规则，不重算历史。

### 7.4 到达上限后的收尾

上限表示最多可使用的资源，不要求跑满。Meta 可以按第 7.4.1 节申请提前结束，用户也可以主动停止；系统保存决定和原因。触发真实资源停止条件、用户停止或有效的 Meta 结束申请时，进入收尾，不再启动新的插件探索或受理新批次。仅轮数或 Trial 准入额度用满时，关闭新增批次准入，已受理批次按第 7.2 节继续，并保留分析和收尾能力；时间或用量不足时，停止启动其剩余 Trial。新资源策略下，单纯由 Meta 计划预留造成的阻塞应通知其调整计划并保持可恢复，不能据此宣称用户额度耗尽或提前结束探索。

收尾必须遵守以下要求：

- 按截止策略处理已启动工作，取消不再允许启动的排队工作，保存部分产物与原始结果。严格截止到期时终止剩余模型调用和实验工作，不以撰写报告为由延长预算。
- 在有效预留的时间和用量内整理每轮报告、生成最终总报告、导出已有保留版本并清理运行资源。收尾预留属于总预算，不能作为额外免费额度；探索不能绕过当前有效预留。新资源策略中 Meta 可以按第 7.2 节修改自己的计划预留，但不能低于用户明确设置的最低值或提高用户上限。
- 未完成的评分、分析、泛化评估或独立运行验收明确列为未完成；需运行的交付验证应事先安排并计入额度，不为完成验收突破上限。停止时不强行晋升新候选，可以保留 H0。
- 强制中断、模型不可用或预留不足时，由系统至少持久保存一份无须模型调用的状态摘要：已完成工作、当前保留版本、实际消耗、停止原因、未完成事项及恢复入口。完整报告未生成时明确标注，不伪装为完整交付。
- “请求终止”与“确认已结束”分别记录。外部运行不能及时确认结束或清理时，标记待核实并保存追踪入口；实际超时和可能的在途消耗如实展示，不自动重试或假装已经停止。

### 7.4.1 探索结束判断

新活动绑定 `goal-or-budget-v1`，仅有两种正常完成条件：

1. **达到用户设定的目标。** 同一冻结版本的完整执行证据满足用户约定的标准，不降低阈值、不拼接不同版本的最好结果。当前可机器核验的入口为用户预先配置的 `stabilityRule`：逐任务最低执行次数与每次官方评分下限；没有该规则时不能由模型自报达标。自由文本目标不会被平台自动解析为数值规则。
2. **活动额度达到上限。** 后台按用户额度、时间与用量进入停止与收尾，已受理工作遵循第 7.2–7.4 节。Meta 自定预留造成的暂时阻塞不能当作额度耗尽。

“无法继续改进”“暂时没有方向”或“充分探索后收益不足”不再是新活动的结束条件。工具仅接受目标达成申请，后台独立拒绝探索耗尽申请和停止审查请求；主会话继续按证据与状态唤醒。用户暂停、停止及外部故障仍按实际原因处理，不能误称为目标达成。

旧活动继续使用其冻结的 `stop-review-v1` 和审查记录，不改写历史提示词、工具或结束依据。历史协议见[停止审查专题](../design/meta-harness-composition.md#5-三类停止条件与审查协议)。

### 7.5 暂停与恢复

用户可以暂停并恢复活动。暂停默认停止新开发调用、批次受理和新 Trial 启动；已启动的模型请求或 Trial 在原有上限内结束并归档，也可由用户选择终止。暂停不等于冻结外部环境或取消已发出的实验动作，相关消耗继续计入。

整体时限采用墙钟口径，暂停、进程退出和断线期间继续计时，绝对截止时刻也不后移。恢复不重置轮数、Trial 数、已消耗与已预留额度；系统先核实外部运行、结算可确认消耗并检查剩余额度，再恢复未启动工作。暂停或离线期间到期的活动恢复后仅处理收尾，不重新开启探索。

中止的 Trial 不假装从原位置继续；再次尝试按新批次、新 Trial 计数。尚未启动且仍获准的原批次工作可以继续，不能因恢复重复扣减轮次或重复启动。需要延长活动或增加预算时，由用户显式调整并保留记录，Meta 无权自行续期。

Meta 通信故障或进程退出与活动终止分开。新运行契约支持有上限、可计量的技术恢复，优先续接原生持久会话；不能续接时显式建立关联的新会话并使用同一工作区及事实入口。恢复前核对操作、进程、通知确认和预算，禁止重复执行已受理实验。恢复耗尽显示可恢复的故障状态，已受理任务继续受监督；不能标作用户暂停或充分探索后停止。恢复策略不改变 Solver 重试与评分规则，具体见[专项设计第 9 节](../design/meta-agent-and-evidence.md#9-会话持久化与恢复)。

### 7.6 脱离 Meta 的最终交付

最终交付包括精简的独立执行项目，以及每轮报告、最终总报告、评估证据和已知限制。执行项目按第 7.7 节打包，报告与历史证据可另附交付，运行时不依赖它们。

执行资产必须持久保存，由独立 loader／profile／preset 装配，不依赖 Meta 插件作用域、临时目录、开发对话、服务或存活进程。卸载可由宿主在完成持久化并处置进行中工作后，通过重新启动实现。

必须在不安装或不加载 Meta 的新会话中验证实际导出的项目：选定版本正确装配、进化工具与开发上下文不进入 Solver、约定任务路径可执行、轨迹和官方评估仍可产生，另行保存的旧报告仍可阅读。此项证明独立运行能力；科学效果由既定评估证据支持，不要求随机运行复现同一次分数。

### 7.7 精简独立执行项目导出

用户必须能够从已保存的冻结候选导出独立 Harness 项目，默认选择最终保留版本，也可明确选择其他候选。导出入口展示短编号与有意义的名称、插件组合、效果证据与独立运行验收状态；待验证候选可导出，但不得因此标为已验证。导出不需要重新运行进化，也不自动创建或发布远端仓库。

**导出根据候选组合清单按需生成项目，测试与交付使用同一套版本解析和装配规则。** 提供选定插件、必要资产、原生启动配置及准确依赖声明，DeepSeek Harness 按所引用版本安装，不随包复制本体或安装缓存。运行所需依赖必须全部明确声明，不默认复制整个执行目录。输出应包含可单独维护的项目源码目录，并支持生成压缩包；具体目录名与压缩格式由实现确定。

| 内容 | 包含与排除规则 |
|---|---|
| 插件与配方 | 包含所选候选的精确插件实现、配置、依赖及必要静态资产；排除未选中的历史版本和失败候选 |
| 框架与启动配置 | 记录 DeepSeek Harness 的准确版本与获取方式，提供所需原生 profile/patch 和启动入口；优先使用框架已有能力 |
| 必要适配 | 逐项确认模型、工具、环境接入与单次监督依赖；仅提供实际需要的明确版本插件、适配代码或可安装包，保留声明的权限和资源边界，不默认附带实验平台 |
| 安装与启动 | 提供项目自己的依赖声明及锁定信息、运行环境要求、配置示例、安装与启动入口；不要求用户手工从原仓库挑选文件 |
| 版本与说明 | 附导出清单、来源候选、运行代码与依赖指纹、导出工具版本、模块用途、默认 Solver 设置、适用范围及已知限制 |
| 演化与开发材料 | 默认排除 Meta 插件、开发模型配置、进化调度与搜索代码、工作台 UI 插件、Meta 开发资料包及查询服务、brainstorm、历史运行、研究报告及无关测试和实验计划；保留执行项目自身必要的安装与维护说明 |
| 凭据与机器状态 | 不包含令牌、登录文件、私有环境变量、缓存、临时目录、已有模型会话或宿主机专属运行状态；认证由使用者在运行时提供 |
| 报告与证据附件 | 可单独导出允许分享的报告和证据包，遵守原有反馈权限；执行项目本身不依赖这些附件 |

独立项目可以依赖明确声明并可安装的 DeepSeek 运行时、语言环境及外部实验服务。Quantum-Harbor 的任务、qsim、官方 verifier 或镜像可作为外部环境提供，不要求将整个实验平台、隐藏任务材料和模型服务一并打包。说明必须列出外部依赖的版本、配置和获取方式；“独立”表示不依赖原开发仓库与 Meta，不默认承诺离线或无依赖运行。

项目内部资源使用可迁移路径。不得通过指向原仓库的绝对路径、符号链接、本地包依赖或导入路径暗中借用源码、`node_modules`、历史 `runs/` 或 Meta 服务。任务环境、模型认证及输出位置通过显式配置提供，新运行产物写入项目自己的输出位置或用户指定目录。

打包由固定导出逻辑完成，解析原组合清单并核对插件内容与依赖身份；不要求复制提前保存的完整项目，不在导出时重新选择依赖版本，也不能让模型重新生成一套近似实现。打包所需的路径或入口调整必须记录并在导出包上验证。若改变插件行为、提示、Solver 设置或工具语义，应作为新候选重新评价，不能沿用原候选的效果结论。

**独立性验收必须针对实际导出包进行：** 将它放在原开发仓库不可访问的新目录或干净环境中，仅按项目说明安装声明依赖、配置认证与外部任务环境，即可装配精确版本并完成约定执行链路。检查导出清单及内容指纹、无关材料与凭据排除情况、配置可迁移性，并确认真实权限、预算和轨迹记录仍生效。不得借用原仓库已有安装来使检查通过。

导出操作展示所选版本、包含内容、外部依赖、包大小、导出结果与验收状态。总报告提供对应入口；完整报告或历史证据作为单独的可选附件。导出、打包检查与真实运行验收分别记录：压缩包生成成功不等于独立运行验收成功，验收未完成或失败时明确标注。交付验收的实验仍计入第 7.2 节的轮次与预算，不因打包另行隐式消耗。

交付页面称为「获取执行 Harness」，默认选择最终保留版本；其他版本通过选择器查看。主操作为下载项目、打开项目目录、查看/下载匹配版本和任务的运行说明。显示精确插件及用途、固定 Solver、已有评分、包内内容与外部依赖；文件检查、独立安装/加载、独立真实实验三项状态分开，不以生成 ZIP 或装配通过冒充真实运行通过。旧冻结包不改写，更新的匹配说明可作为独立附件下载。

### 7.8 工作台 UI 插件与后台独立运行

UI 允许多个设计方案独立演进、并存体验和淘汰。各版 UI 不依赖其他版本的源码或存活，共享客户端能力独立于具体界面。删除一版或替换页面不影响其他版本和后台数据；默认版本提供完整必需操作路径，试验版明确功能范围。状态和样式按版本隔离，跨版本草稿兼容显式定义；切换和删除不重复创建活动或发出后台控制命令。见[UI 模块化设计](../design/meta-workbench-modularity.md)。

第一版优先通过 DeepSeek Harness 原生客户端扩展提供工作台入口和主面板，复用适用的布局、主题和导航能力。独立 Web 外壳作为后续可选扩展，不要求首版同时维护两套界面。原生接入的可行性、构建和生命周期必须在开发初期验证，不以修改 DeepSeek 核心代码为默认接入方式。

工作台必须支持配置两个模型与活动规则、启动/暂停/恢复/停止、查看候选和测试状态、比较结果、读取报告与证据、导出独立项目及查看验收状态。用户调整上限和模型配置的权限不能因 UI 与 Meta 共用后台而授予 Meta。工作台和宿主适配代码属于固定实现，不属于本轮自进化修改范围。

操作必须有当前可见的反馈：报告入口立即显示读取状态，加载后定位到正文；创建活动时解释无效配置与后台拒绝原因，保留输入，不能让用户在屏幕外寻找错误。提交中防止重复操作，创建成功明确显示新活动。轮次、时间、并发及预算等数值只允许直接输入或点击右侧上下按钮调整，滚动页面或滚轮悬停不能改变数值。此项适用于新建配置和调整上限。

UI 展示后台权威状态，不能自行维护另一份轮数、预算或结果。刷新、断线、卸载与重新加载 UI 后，能够重新读取同一活动状态；后台计时、已有任务监督和记录持续生效。后台也不能依赖 UI 来唤醒 Meta、收集完成结果或执行截止处理。后台暂不可用时，界面显示连接状态和可能陈旧的数据，不假装任务已停止或完成。

UI 插件不进入 Solver profile 或独立执行项目。报告继续支持持久、离线阅读，不因工作台插件卸载而失去访问能力。UI 原生接入和第 3.1.1 节开发资料/查询的版本匹配验证，均纳入 M0 技术验证阶段。

| 完整材料与长输出 | 评分详细指标、轨迹及输出末尾均可按路径读取；失败和超时保留部分原件，分页/压缩不破坏完整来源 |

| 组合与测试 | 精确组合可冻结并完成一次真实 Quantum-Harbor 官方评估；支持不同任务数量与重复次数，全部尝试可追溯 |

| 版本任务表现与进度 | 概览默认可见成功数/分母、成功率及运行/排队；展开范围与汇总一致，未测/无结果/失败分开，历史快照不混入新结果 |
| 选择及主要备选 | 理由、代价、明确考虑过的备选和重选条件可读；缺少备选分析不臆造拒绝理由，选择不冒充效果认证 |
| 跨活动问题来源 | 显式纳入的历史材料可定位原活动、实验和片段；未纳入来源拒绝，旧分析不升级为事实，历史成绩不进入当前分母 |
| 最终总报告 | 清楚展示起点、最终选择、关键转折、效果与代价、插件组成、泛化范围、配置上限与实际消耗、停止原因及交付入口 |
| 轮次与准入 | 1 个候选 × 5 个任务 × 2 次重复计 1 轮、计划 10 次 Trial；追加批次和失败尝试计数，重复收集不计数，最后一轮可在预留额度内完成 |
| 时间、用量与并行 | 多个上限同时生效，并发不重复占用余额；严格截止终止剩余工作，允许当前任务结束模式单独记录超出时间，软阈值不冒充硬上限 |
| 暂停与恢复 | 暂停阻止新工作，外部运行按策略处置；计时和消耗不重置，恢复不重复受理或启动，已到期仅收尾 |
| 收尾与中断 | 预留资源用于报告、导出与清理；不足时仍有系统状态摘要，未评分、未验证、未清理事项不被伪装为完成 |
| 版本与边界 | 测试期间候选不可变；检查失败不进入正式效果测试；Meta 无权自行增加上限或延长期限 |
| 负结果与独立运行 | 无提升时允许保留 H0；最终配方在无 Meta 的新会话中可运行，报告和证据仍可访问 |
| 插件版本与缓存复用 | 同一插件内容只保存一次；候选以组合清单引用；相同锁定依赖在兼容平台上共享安装，缓存重建不改变身份或丢失源码 |
| 精简项目导出 | 按组合清单生成选定插件、必要适配、配置、依赖声明与启动说明；DeepSeek 按准确版本安装，排除 Meta、无关研究材料、凭据和机器缓存；报告可另附 |
| 导出包搬迁验收 | 在原开发仓库不可访问的环境中，仅使用声明依赖与外部配置完成约定执行链路；无原仓库路径或服务依赖，版本与权限边界可核对，验收状态如实展示 |

系统能力验收与研究效果验收分开。四类能力、边界和独立运行通过，说明系统能开展自进化实验；只有足够且可比的评估才能支持稳定改进，只有相应独立任务或实例证据才能支持泛化。首版可以交付真实、可复核的负结果。

## 10. 模型异常流保护与故障可解释性补充

模型请求须具备固定宿主执行的有限时间、接收内容大小和高置信异常工具参数保护。输出 token 限制只有在提供方实际支持并验证后才能标记为硬限制；本地字节计数、可见输出估算和取消均不能冒充计费硬上限。异常结束保留所有已启动尝试、原始证据和未知用量，不执行截断的工具调用。新 H0 v2 的 Solver 内置五档有限请求恢复：连接失败、断线、响应不完整及明确过载后等待 2、5、20、30、60 秒，保留已完成工具结果，并覆盖原生上下文压缩。所有调用仍受固定模型、预算和原截止约束；旧配方及旧冻结对象保留原策略，不自动重跑整个 Trial。请求失败历史与任务最终失败分别记录，恢复成功不能被首次错误污染。Solver 实施与验收见[请求恢复计划](../plans/model-request-recovery.md)；新 Meta 的有限技术恢复遵循第 7.5 节，不追溯改变旧活动。

工作台与报告须区分运行中等待评分、已结束未评分、官方零分，明确故障阶段、具体原因、终止方式及证据。模型故障不能被外层收集错误或清理退出码遮蔽。Meta 应能查询同一摘要并获知单次结束；旧结果仅追加有来源的诊断和展示修订，不修改原分析与原始评分。

模型接入诊断须区分模型内容与传输协议进度，关联请求、连接、复用和回退，保留可用的关闭码及脱敏底层原因。连接故障最终未恢复时按活动 v2/v3 规则计任务完成分 0，官方缺失评分保留 null；单次失败不提前判任务失败，成功恢复不受历史错误污染，平台自身故障仍单列。缺失观测保持未知，诊断不得隐式改变 Meta 的恢复策略。
