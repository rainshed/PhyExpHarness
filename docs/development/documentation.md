# 文档维护规则

状态：持续适用。完整目录维护在[docs/README](../README.md)，根 README 介绍项目和最短入口，AGENTS 保留开发规则与代码导航。

## 唯一职责与来源

| 内容 | 权威位置 |
|---|---|
| 目标、价值、产品约束 | product |
| 当前用户操作 | guides |
| 当前模块机制、理由与兼容 | architecture |
| 开发、验证、提交和维护 | development |
| 尚未完成的工作 | plans |
| 被替代的设计、旧计划、旧运行说明 | archive |
| 执行 SDK 教学资料源 | knowledge/plugin-sdk |
| 字段/默认值、命令 | 对应 schema/源常量、package.json |

一个规则只在一处完整解释，其余通过链接引用。文档描述代码实际状态；产品要求与实现存在差距时必须显式登记，不能为“对齐”删掉用户要求或把未实现能力写成已经可用。

## 更新方式

功能变化时改写当前正文，移除失效描述。不要靠顶部“以后文为准”保留一整篇互相矛盾的操作规则，不不断追加日期增量让读者拼版本。

当前页面写清适用契约、操作前提和已知限制；数值字段优先链接 schema/常量。涉及历史支持时集中更新兼容页，不把仍在支持的行为只藏在归档。

计划列出目标、状态、未完成项和可验证完成条件。实现后将最终规则移入当前文档，计划归档；归档本身不等于所有验收通过。旧计划中的授权、执行者与阶段要求不自动适用于新任务。

## 迁移和归档

本次将旧 design/requirements/operations 的混合稿和旧开发计划保留在 archive 对应子目录，正文历史状态不作为当前承诺。设计哲学迁到 product，当前规范按职责重新撰写。旧路径与新入口在[历史索引](../archive/README.md)逐项对应。

移动时更新相对链接、锚点、README、AGENTS、包说明和机器读取的 SDK 指南；代码/脚本内有实际路径依赖时一并调整。不保留多个含正文的“新旧现行副本”。SDK 生成器仍读取原资料源位置，现行 docs 不替代其生成入口。

归档保留历史正文及可解析的来源链接，可以修复旧错误链接，不能据当前状态改写过去验收结论。当前页面只能将 archive 索引用于历史导航，不能把归档设计作为当前操作前提。

## 检查与验收

运行 `npm run check:docs` 检查本地 Markdown 链接、目标标题锚点、当前页面可达性及归档引用边界；生成目录、本地记录和外部网址不作为该检查的语义验证对象。链接通过不表示内容正确。

功能声明需对应[实现核对表](implementation-audit.md)中的实现和有意义的测试，核对创建默认、数据来源、状态转换、权限、兼容与错误路径。改动 SDK 指南后还要重建资料并验证生成包内容。记录本轮实际检查范围及没做的验证，不能复述历史“通过”作为当前结论。

提交前检查没有将本地记录、密钥、现场配置或生成目录纳入 Git，再运行 `npm run check:project`。
