# 开发流程与仓库约定

状态：持续适用的开发规则。按当前用户授权范围工作；阅读计划或历史任务书不会自动启动额外重构、真实实验、历史清理或实例发布。

## 开始与完成

先读取根 [AGENTS.md](../../AGENTS.md)、[设计哲学](../product/philosophy.md)、相关当前架构及实现。保留用户改动、历史实验和原始证据，从已经存在的有效成果继续。内部实现选择在授权范围内自行处理，不能削弱固定模型、隔离、证据、官方评分和独立交付边界。

先实现可验证的小流程，再扩展覆盖。完成相关检查并处理失败，不将脚本、骨架或静态页面当作完整产品验收。模拟测试、容器契约、真实模型调用、官方评分、搬迁运行及用户接受分别记录，不把其中一层写成全部通过。

真实调用先核对现有授权、模型、任务范围和运行上限；已有授权继续适用，缺少必要输入时准备具体运行范围再询问。新活动没有平台 token 账本，不能把外部费用控制误写成现成平台能力。失败和先前尝试保留，不通过换活动清除成本事实。

## 源码与依赖

目录职责见[架构总览](../architecture/overview.md)。生成候选代码在隔离环境运行，控制服务不在宿主直接加载其声明或插件。执行侧不能依赖控制、报告或 UI；各 UI 使用公共客户端公开入口。新增动态资产必须纳入准确清单与独立导出验证。

SDK、schema、模板及代码变更需同步核对新活动绑定和旧冻结读取，不能直接修改历史对象来升级行为。资料源更新运行 build:knowledge，UI 更新运行 build:workbench；源码重建不热替换运行进程。

## 验证与提交

每完成一个独立功能或修复并通过相关验证后，立即本地提交，无需再次确认；独立文档、配置修改同样适用。标题采用 `<type>(<scope>): <中文说明>`。提交前运行 `npm run check:project`；文档变更运行 `npm run check:docs`，相关行为检查按[验证说明](testing.md)选择。

保留失败原因、修复及实际覆盖，不因一次全套已通过反复运行昂贵检查；新变更、失败或证据缺口才扩大验证。提交不自动包含推送、公开发布或实例切换。

## 主线与部署职责

主线维护独立项目功能、标准 Docker/Harbor、本地存储、通用配置和可搬迁交付。机器专属运行时、远程归档/恢复、服务管理、网络和发布步骤由部署分支维护；其专属测试和现场记录随部署实现。通用改进先进入主线，再由部署分支同步，部署专属改动不整体合回主线。

`check:project` 检查模块依赖及部署内容回流，覆盖源码、配置、脚本、测试、模板与正式文档。历史 Git 保留，不重写历史；外部实例的数据转换与切换由部署侧独立核验。

## 入库与本地记录

以 [.gitignore](../../.gitignore) 为准，提交源码、可复用配置、schema、依赖锁、模板、合成测试夹具及正式文档。

- runs、reports、.runtime、外部数据目录、实验结果、轨迹、截图和授权/验收日志不提交。
- docs/brainstorm 是本地讨论稿，正式文档不能依赖它或私人路径。
- knowledge/plugin-sdk/reference 和 UI lib 是生成目录；提交其资料源、脚本和锁。
- 依赖、虚拟环境、缓存和个人配置不提交。生成插件只有经用户决定长期维护并整理为源码后才入库。

`src/reporting` 是实现，`reports` 是本地输出；`templates/standalone` 是模板，实际 ZIP 在数据目录。忽略不等于删除或备份。不得用清理工作区的命令破坏被忽略的实验记录。

本地开发记录保存改动标识、检查命令/环境/退出状态、覆盖、失败、在途工作、证据路径和下一步。新克隆没有本地报告时，从代码和可执行检查重建判断，不推断历史验收已经通过。文档内容归属见[文档维护](documentation.md)。
